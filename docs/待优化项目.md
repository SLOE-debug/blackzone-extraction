# 一、一直按住攻击键确实有效，问题不在按钮

攻击按钮已经正确维护了两个状态：

```ts
attackPressed // 按下边沿
heldValue     // 持续按住
```

触摸开始时会同时设置 `heldValue = true` 和 `attackPressed = true`，触摸结束或取消才清除持续状态。

HUD 每帧也确实把它们写成：

```ts
attackPressed = consumeAttackPress()
attackHeld = attackButton.held
```

所以你观察到的“动作结束马上进入闲置”，并不是按住状态丢失，而是后面的攻击状态机主动回到了 `Idle`。

# 二、普通攻击必然出现一帧 Idle

## 当前调用顺序

```text
Input
  BattlefieldWeaponInputWorldSystem

PreSimulation
  BattlefieldWeaponWorldSystem
  BattlefieldPlayerWorldSystem
  BattlefieldWeaponPoseWorldSystem
```

输入系统只有在：

```ts
weapon.acceptingActionCommand === true
```

时才会提交下一次挥动，而该属性仅在动作已经是 `Idle` 时为真。

但是输入系统运行在动作状态更新之前，因此实际发生的是：

```text
第 N 帧 Input
  当前动作仍然是 Recover
  acceptingActionCommand = false
  即使 attackHeld = true，也不会提交下一击

第 N 帧 Weapon
  Recover 到期
  finishAction()
  动作立即变成 Idle

第 N 帧 Player / Pose
  人物按 Idle 姿态渲染

第 N+1 帧 Input
  此时才看到 Idle
  提交下一次 Windup
```

`Recover` 到期后确实直接执行 `finishAction()`，将状态改为 `Idle`。

角色系统又在武器状态更新之后读取这个新状态，所以这一帧的 Idle 会真实进入人物动画，不只是内部状态。

在 60 FPS 下至少是约 16.7 ms；移动端掉到 30 FPS 时是约 33 ms，帧抖动时还会更明显。

# 三、即使消除这一帧，当前连击仍然不会丝滑

现在的左右攻击实际上是两次完全独立的动作：

```text
Idle
→ WindupLeft
→ SwingLeft
→ Recover
→ Idle

Idle
→ WindupRight
→ SwingRight
→ Recover
→ Idle
```

测试也明确要求先把第一击完整推进到 `Idle`，之后才能请求第二击。它没有测试“持续按住时直接衔接下一击”。

所以你的视觉描述非常准确：

```text
左侧起手
→ 挥向中间或另一侧
→ 完整回到闲置提锤姿态
→ 再从闲置姿态前往右侧起手
→ 再挥向中间
```

这不是连续左右抡锤，而是不断播放“单次攻击动画”。

# 四、轨迹函数还在每个阶段强制刹停

普通攻击的三个阶段分别使用独立的 `smootherStep()`：

```ts
Windup:
  IDLE_POSE → WINDUP_POSE

Swing:
  WINDUP_POSE → FOLLOW_THROUGH_POSE

Recover:
  FOLLOW_THROUGH_POSE → IDLE_POSE
```

`SmootherStep` 是：

```ts
t³ × (t × (t × 6 - 15) + 10)
```

它在 `t=0` 和 `t=1` 的速度都为零。于是每次攻击实际上会：

```text
蓄力结束：速度降到 0
挥击开始：从速度 0 再加速

挥击结束：速度降到 0
恢复开始：从速度 0 再加速

恢复结束：速度降到 0
下一次蓄力：从速度 0 再加速
```

代码注释认为这样实现了“位置和速度连续”，数学上确实是连续的，但所有边界的共同速度都是 **零**。视觉结果就是不断启动、刹停、再启动。

这正是“动作会突然停下来”的第二个根因。

# 五、状态更新时间还会丢掉跨阶段的剩余时间

阶段到期后，`beginAction()` 会直接执行：

```ts
elapsed = 0;
```

而不会保留：

```ts
elapsed - previousDuration
```

例如本帧剩余 20 ms，但当前阶段只剩 5 ms：

```text
正确行为：
  先推进当前阶段 5 ms
  再把剩下 15 ms 推进到下一阶段

当前行为：
  推进当前阶段
  切换动作
  剩余 15 ms 被丢弃
```

这会使阶段时长随帧率变化，并在低帧率时产生额外停顿。

命中后还有一个额外的 45 ms `Hit Stop`，期间动作时间完全不推进。

Hit Stop 本身可以保留，但它与阶段零速度、Idle 插帧叠加后，就会显得非常僵硬。

# 六、普通攻击正确方案：连续双击循环，而不是重复单击

## 新状态结构

建议将普通攻击重构成：

```text
IdleCarry
  ↓ 首次按下
FirstWindupLeft
  ↓
SwingLeft
  ↓
LeftFollowThrough
  ├─ 持续按住 → ChainPrepareRight
  └─ 已松开   → RecoverToIdle

ChainPrepareRight
  ↓
SwingRight
  ↓
RightFollowThrough
  ├─ 持续按住 → ChainPrepareLeft
  └─ 已松开   → RecoverToIdle
```

核心区别是：

```text
SwingLeft 结束姿态
≈ 下一次 SwingRight 的起手姿态

SwingRight 结束姿态
≈ 下一次 SwingLeft 的起手姿态
```

不再经过 Idle。

当前轨迹已经具备接近这个关系的关键帧：

* `LEFT_FOLLOW_THROUGH_POSE` 和 `RIGHT_WINDUP_POSE` 的锤杆方向相同；
* `RIGHT_FOLLOW_THROUGH_POSE` 和 `LEFT_WINDUP_POSE` 的锤杆方向相同。

但它们目前从未直接连接，而是中间强制经过 `IDLE_POSE`。

---

## 输入不应只在 Idle 时提交

删除这种门禁：

```ts
acceptingActionCommand =
  action === WeaponAction.Idle;
```

替换为两个含义明确的状态：

```ts
needsInitialSwingAim: boolean;
canBufferNextSwing: boolean;
```

输入链路应变为：

```text
attackHeld 每帧持续写入武器运行时

Idle
  → 请求首次攻击方向

当前攻击进入连段缓存窗口
  → 若仍按住，提前请求下一击方向
  → 写入 queuedSwing

当前攻击结束
  → queuedSwing 存在：直接进入相反侧连段
  → queuedSwing 不存在：恢复到 Idle
```

推荐预输入窗口约为动作结束前 `100–160 ms`，避免等待下一帧才提交。

自动锁敌仍然只在“新一击开始前”重新解析，不能在挥动中途改变方向。

---

## 轨迹改成共享切线的连续曲线

不要继续对每两个关键帧单独套 `smootherStep`。

建议使用三次 Hermite 或 Catmull–Rom：

```ts
interface HammerTrajectoryKeyframe {
  position: HammerPose;
  tangent: HammerPoseVelocity;
}
```

左右循环可以定义为：

```text
LeftReady
→ LeftImpact
→ RightReady
→ RightImpact
→ LeftReady
```

每个相邻阶段共享端点切线：

```text
前一段结束速度
==
后一段开始速度
```

这样锤头在左右循环中会持续运动，而不是每经过一个关键帧就停下。

只有以下节点应允许速度接近零：

```text
最初 Idle
玩家主动松开后的最终 Idle
重砸蓄力顶点
明确设计的 Hit Stop 接触帧
```

普通左右连段中间不应归零。

---

## 时间推进必须保留剩余帧时间

```ts
let remaining = Math.min(deltaTime, 0.05);
let transitions = 0;

while (remaining > 0 && transitions < 4) {
  const available = duration - elapsed;
  const step = Math.min(remaining, available);

  elapsed += step;
  remaining -= step;

  if (elapsed >= duration) {
    transitionToNextState();
    transitions++;
  }
}
```

这可以避免不同帧率下产生阶段空档。

# 七、旋风技能的判定范围确实接近视觉的两倍

当前旋风没有使用真实锤头扫掠，而是以玩家为圆心做全圆查询：

```ts
query.origin = player.position

query.reach =
  definition.reach * 1.12

query.arcRadians =
  Math.PI * 2
```

大锤基础射程是：

```ts
reach = 3.9
```

因此旋风查询半径为：

```text
3.9 × 1.12 = 4.368
```

而视觉锤头的代码尺寸是：

```text
锤柄主握点到锤头：
3.08 × heldScale 0.45
= 1.386

旋风主握点距离人物中心：
约 0.72
```

因此视觉锤头中心的最大平面半径大约是：

```text
0.72 + 1.386 × 0.993
≈ 2.10
```

碰撞半径和锤头中心轨迹半径之比：

```text
4.368 ÷ 2.10
≈ 2.08 倍
```

即使把锤头模型自身半径也算上：

```text
锤头半径：
0.82 × 0.45
≈ 0.369

视觉最外缘：
2.10 + 0.369
≈ 2.47
```

当前 4.368 的判定仍然约为视觉外缘的 `1.77 倍`。

而怪物查询时还会把怪物自身碰撞半径加到攻击射程上，所以怪物中心甚至可以略微超过 4.368 仍然被命中。

这完全可以解释“隔很远也会被攻击到”。

当前普通攻击和上挑已经使用：

锤头位置也确实来自与 Renderer 相同的模型姿态。

  玩家中心 4.368 米圆

这不是参数微调问题，而是判定模型选错了。

# 九、旋风还存在“双重旋转源”

动作状态会让角色朝向旋转三圈：

```ts
lockedHeading =
  initialHeading + progress * Math.PI * 6;
```

同时，武器局部轨迹又让锤杆相对角色旋转三圈：

```ts
angle = normalizedProgress * Math.PI * 6;

shaftX = cos(angle);
shaftZ = sin(angle);
```

由于 WeaponRoot 最终还会应用角色世界朝向，因此锤头世界角度近似是：

```text
角色旋转角
+
锤杆局部旋转角
```

这会造成：

* 人物转三圈；
* 锤子相对人物又转三圈；
* 世界空间锤头看起来接近转六圈；
* 角速度在技能前后还不均匀。

必须只保留一个旋转权威。

推荐方案是：

```text
动作状态：
  输出 spinAngle

角色 Root：
  initialHeading + spinAngle

骨盆、胸腔、双臂、WeaponRoot：
  整体跟随角色旋转

锤杆局部：
  保持水平固定姿态
  只叠加少量惯性滞后
```

删除轨迹中的额外 `Math.PI * 6` 局部旋转。

# 十、旋风正确判定方案

## 判定必须来自视觉锤头扫掠

旋风期间每帧使用现有锤头状态：

```text
previousHead
→ currentHead
→ Swept Capsule
```

不要再使用：

```ts
definition.reach * 1.12
```

建议：

```ts
spinSweepRadius =
  visualHammerHeadRadius + gameplayAssistMargin;
```

其中辅助余量控制在约 `0.10–0.20`，用于补偿视觉轮廓和低帧率，而不是扩大到两倍。

---

## 保留脉冲频率，但每个脉冲内连续扫掠

目前旋风每 `0.32 秒`产生一次新攻击序列。

可以继续保留伤害节奏，但应改成：

```text
每帧收集视觉锤头扫掠
  ↓
当前 0.32 秒窗口共用同一个 attackSequenceId
  ↓
同一怪物在本窗口最多命中一次
  ↓
进入下一个窗口时生成新 attackSequenceId
```

这样既不会漏掉高速锤头，也不会每帧重复伤害。

调用链：

```text
WeaponPoseWorldSystem
  → Renderer.setRigPose()
  → 得到真实 headX/headZ
  → HammerHeadSweepState.synchronize()

HammerSweepWorldSystem
  → action === Spin
  → collectMeleeSweepHits()
  → 当前脉冲 attackSequenceId 去重
  → Damage / Knockback / Magnetized
```

---

## 最终震波必须可视化，否则删除扩大判定

旋风最后一击可以比锤头扫掠稍大，但必须显示明确的地面冲击环：

```text
视觉冲击环半径
==
最终判定半径
```

若没有冲击环，就只能使用真实锤头轨迹，不能悄悄扩大范围。

# 十二、必须补充的验收测试

## 普通攻击

1. 持续按住攻击两秒，第一击后不得出现任何 `Idle` 帧。
2. 左右连段必须直接连接，不经过 `IDLE_POSE`。
3. 连段阶段边界的位置与速度都连续。
4. 30、60、120 FPS 下，两秒内的挥击次数和接触时间基本一致。
5. 单帧跨越阶段边界时，剩余时间必须进入下一阶段。
6. 松开按钮后完成当前随挥，再平滑回到单手 Idle。
7. Hit Stop 期间仍然允许缓存下一次连段。
8. 自动目标只能在每次新挥击前改变，挥击过程中保持锁定。

## 旋风

1. 世界空间视觉锤头只旋转三圈，而不是角色三圈加局部三圈。
2. 判定轨迹必须与上一帧、当前帧锤头连线重合。
3. 位于视觉锤头外缘加辅助余量之外的怪物不得受伤。
4. 位于锤头真实扫掠路径上的怪物必须受伤。
5. 同一脉冲窗口内同一怪物最多命中一次。
6. 最终震波判定半径必须与可视冲击环一致。
7. Debug 模式应同时绘制锤头轨迹、胶囊半径和实际命中目标。
