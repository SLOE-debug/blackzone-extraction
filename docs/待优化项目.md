我查看了最新提交 `ebd57e0`：**“fix: 修正猎弓三维弹道与远距召回表现”**。这次掉帧并不是某一个数值配置造成的，而是最新提交把几项高成本工作叠加进了同一帧热路径。

## 结论

当前性能回归的优先级大致是：

1. **弦网每帧复用投射物的精确三维胶囊碰撞，成本最高。**
2. **Crowd 候选去重是线性扫描，长线段查询会出现近似二次复杂度。**
3. **箭矢 Renderer 每帧重写并上传整个批次，没有利用现有 `dirty` 标记。**
4. **几何生成每帧创建大量临时 `Point` 对象，造成 GC 压力。**
5. **动态包围盒在箭向外飞行时可能连续调用 `onGeometryChanged()`，产生尖峰。**
6. 垂直辅助瞄准只在真正发射时执行，**不是持续掉帧的主要来源**。

最关键的问题是：你把“需要准确首次接触时间的高速箭矢检测”，直接复用到了“持续五秒、最多六条、每帧检测的弦线”上。

# 一、最大热点：12 轮二分被弦线每帧调用

最新增加的三维胶囊求交函数，在宽相位候选通过后：

* 先计算线段与胶囊中轴最近点；
* 再进行最多 **12 轮二分**；
* 每轮重新执行一次三维距离计算。

这个算法用于普通箭和召回箭可以理解，因为箭需要：

* 找到第一次接触位置；
* 按命中进度排序；
* 支持穿透；
* 正确附着在表面。

但弦网也调用了同一个 `collectArrowSweepHits()`：

```ts
target.collectArrowSweepHits(this.query, this.hits);
```

而且最多六条弦线，当前每一帧全部执行。

假设每条长弦线产生 40～80 个候选：

```text
6 条弦线
× 60 帧
× 40～80 个候选
× 12 轮精确距离计算
```

在移动端或 JSB 环境里，这足以让 Weapon 阶段明显增加数毫秒。

## 修法：弦线必须使用独立查询

新增：

```ts
collectTetherOverlapHits(
  query: BattlefieldTetherQuery,
  result: BattlefieldArrowHitBuffer,
): number;
```

弦线不需要“首次接触时间”，只需要判断怪物当前胶囊是否与线段重叠，因此可采用：

1. XZ 平面点到线段平方距离；
2. 用投影进度得到弦线对应的 Y；
3. 判断该 Y 是否进入怪物竖直胶囊范围；
4. 不执行任何二分。

伪代码：

```ts
const progress = clamp01(
  dot(targetXZ - startXZ, segmentXZ) / segmentLengthSquared,
);

const nearestX = startX + segmentX * progress;
const nearestZ = startZ + segmentZ * progress;
const lineY = startY + segmentY * progress;

const planarDistanceSquared =
  square(targetX - nearestX) +
  square(targetZ - nearestZ);

const maximumPlanarDistance = tetherRadius + targetRadius;

if (planarDistanceSquared > maximumPlanarDistance ** 2) {
  continue;
}

const minimumBodyY = centerY - halfHeight - tetherRadius;
const maximumBodyY = centerY + halfHeight + tetherRadius;

if (lineY < minimumBodyY || lineY > maximumBodyY) {
  continue;
}
```

这会把每候选的成本从十几次函数和距离运算，降为一次投影和两次简单判断。

# 二、弦网没必要按照 60Hz 检测

弦线命中冷却本身是 `0.45` 秒，但当前仍然每帧重新执行完整宽相位和窄相位，最后才通过冷却表拒绝重复伤害。

这意味着一个已经命中过、未来 0.45 秒不可能再次受伤的怪物，系统仍然会：

1. 进行 DDA 宽相位；
2. 加入候选；
3. 执行三维胶囊检测；
4. 加入命中缓冲；
5. 扫描冷却槽；
6. 最后才返回“不允许命中”。

## 立即可做的降频方案

将弦网检测降低到 **15～20Hz**：

```ts
const TETHER_QUERY_INTERVAL = 1 / 20;

private queryAccumulator = 0;

public update(deltaTime: number): void {
  this.queryAccumulator += deltaTime;

  if (this.queryAccumulator < TETHER_QUERY_INTERVAL) {
    return;
  }

  const queryDelta = this.queryAccumulator;
  this.queryAccumulator %= TETHER_QUERY_INTERVAL;

  this.resolveTetherCollisions(queryDelta);
}
```

从 60Hz 降到 20Hz，弦网碰撞工作量直接降低约三分之二，而玩家基本感受不到差异。

更平滑的方式是按边分帧：

```text
帧 0：检测边 0、1
帧 1：检测边 2、3
帧 2：检测边 4、5
```

这样单帧不会同时处理六条长线。

### 防止低频检测漏怪

可以把查询半径增加：

```ts
effectiveRadius =
  tetherRadius +
  maximumMonsterSpeed * queryInterval;
```

或者真正使用怪物 `previousX/Y → currentX/Y` 的扫掠轨迹检测是否跨过弦线。

# 三、Crowd 候选去重存在近似 O(n²)

`collectSegmentCandidates()` 使用 DDA 遍历线段经过的网格，并访问每个主网格周围的邻域。同一个怪物很容易被相邻网格重复访问。

当前候选缓冲的去重方法是：

```ts
for (let index = 0; index < candidateCount; index++) {
  if (samePopulation && sameEntity) {
    return;
  }
}
```

也就是说，每加入一个候选，都线性扫描此前所有候选。

候选数量为 80 时，一次查询的去重比较次数可能接近：

```text
1 + 2 + 3 + ... + 80 ≈ 3200
```

再乘六条弦线和每秒六十帧，成本会迅速放大。

## 修法：使用查询 Stamp 去重

`PlanarCrowdSeparationSystem` 内部已经有稳定的全局 `slot`，最适合在这里完成 O(1) 去重：

```ts
private visitedQuery = new Uint32Array(capacity);
private querySequence = 0;

private beginCandidateQuery(): number {
  this.querySequence++;

  if (this.querySequence === 0xffffffff) {
    this.visitedQuery.fill(0);
    this.querySequence = 1;
  }

  return this.querySequence;
}
```

收集格子时：

```ts
if (this.visitedQuery[slot] === querySequence) {
  continue;
}

this.visitedQuery[slot] = querySequence;
result.appendUnchecked(populationId, entityId);
```

随后删除 `PlanarCrowdCandidateBuffer.include()` 中的线性扫描。

这是通用优化，会同时受益于：

* 弓箭；
* 弦网；
* 大锤连续扫掠；
* 动量传播；
* 未来所有线段查询。

# 四、Renderer 每帧全量重建，`dirty` 完全没被使用

箭池已经有：

```ts
public readonly dirty = new Uint8Array(...);
```

但 Renderer 仍然每帧：

* 遍历全部 24 个箭槽；
* 重写全部箭矢顶点；
* 重写六条弦线；
* 重写六个锚点；
* 重写箭袋；
* 上传整个 Position Buffer；
* 上传整个 Color Buffer。

其中只有六支永久箭会正常启用，但另外十八个临时槽位也会在每帧重复执行 `collapse()`，把已经隐藏的顶点再次写成隐藏状态。

最新几何共有：

```text
24 × 18 个箭顶点     = 432
6 × 12 个弦线顶点   = 72
6 × 24 个锚点顶点   = 144
箭袋                 = 36
总计                 = 684 顶点
```

代码中的容量公式也正是这一结构。

每帧上传的数据量约为：

```text
Position：684 × 3 × 4 = 8208 字节
Color：   684 × 4 × 4 = 10944 字节
合计约 19 KB/帧
```

数据带宽本身不算大，但问题是：

* 每帧进行两次 GPU Buffer 更新；
* JS 侧重复写入所有 TypedArray；
* 很多静态内容也在不断更新；
* Buffer 更新可能触发 JSB/驱动同步；
* 所有工作都发生在 Weapon 的 PreSimulation 阶段。

`arrowRenderer.synchronize()` 就在 `weapon.updateActions()` 内执行，因此这部分动态几何 CPU 工作会直接算进 Weapon 阶段和引擎 Game Logic，而不是独立的渲染阶段。

## 优化顺序

### 1. Color 不要每帧上传

箭、弦线和锚点的 RGB 基本是固定的。

应在初始化时写入颜色，运行时只有以下情况需要改变 Alpha：

* 箭槽激活或释放；
* 弦网激活或关闭；
* 锚点显示或隐藏。

平常移动只上传：

```ts
MeshDirty.Position
```

而不是：

```ts
MeshDirty.Position | MeshDirty.Color
```

### 2. 隐藏槽只初始化一次

十八个临时箭槽在创建 Renderer 时折叠一次，之后没有状态变化就不要再写。

弦线和锚点关闭时也只在“从可见变成隐藏”的那一帧折叠一次。

### 3. 使用 Dirty Range

现有 `DynamicMeshBatch` 已经支持：

```ts
uploadVertexAttributeRange(...)
```

因此可以按区域上传。

建议记录：

```ts
minimumDirtyVertex
maximumDirtyVertex
positionDirty
colorDirty
```

箭槽更新：

```ts
markDirtyRange(
  arrowIndex * ARROW_VERTICES_PER_SLOT,
  ARROW_VERTICES_PER_SLOT,
);
```

最后每帧最多上传一个合并后的 Position 区间。

### 4. 静止世界箭不要重写

不同状态的更新规则：

| 状态                | 是否每帧更新      |
| ----------------- | ----------- |
| Ready             | 仅玩家位置或朝向变化时 |
| Drawing           | 弓挂点变化时      |
| Flying            | 是           |
| Returning         | 是           |
| EmbeddedInMonster | 怪物姿态变化时     |
| EmbeddedInWorld   | 否           |
| 未启用临时槽            | 否           |

### 5. 弦线只在端点变化时更新

* 两端都是地面箭：激活时写一次。
* 一端插在怪物身上：对应怪物或箭 dirty 时更新。
* 两端都静止：不要每帧重写。

# 五、几何写入每帧创建大量小对象

当前几何代码使用：

```ts
point(x, y, z)
```

返回普通 JS 对象。

每支可见箭会创建十多个临时 Point；每条弦线创建八个；每个锚点创建六个；箭袋还会持续创建更多临时点。

弦网开启时大约会产生：

```text
箭矢：  6 × 14 ≈ 84 个对象
弦线：  6 × 8  ≈ 48 个对象
锚点：  6 × 6  ≈ 36 个对象
箭袋：             ≈ 24 个对象
合计：             ≈ 192 个对象/帧
```

60 FPS 下约为一万多个短生命周期对象每秒。

桌面浏览器可能勉强承受，但在移动端或 JSB 环境容易导致频繁小 GC，表现就是：

* 平均帧率在 40 左右；
* 偶尔突然落到 30；
* Logic 最大耗时明显高于平均值。

## 修法

不要再传 `Point` 对象，改为数字参数：

```ts
writeQuadXYZ(
  geometry,
  vertex,
  ax, ay, az,
  bx, by, bz,
  cx, cy, cz,
  dx, dy, dz,
);
```

或者直接使用局部数值写 TypedArray。

颜色也不要在每个 `writeVertex()` 中重复写，只在初始化和显隐变化时写。

# 六、动态 Bounds 可能制造额外尖峰

当箭不断向外飞时，当前 Bounds 会不断扩大。一旦内容超出现有范围，就会调用：

```ts
this.batch.updateBounds(bounds);
```

而 `updateBounds()` 内部会执行：

```ts
this.renderer.onGeometryChanged();
```

这可能导致 Renderer 重新处理几何状态。

由于箭每帧都可能刷新一个新的最远位置，向外飞行期间可能连续多帧更新 Bounds。

## 修法

不要按厘米级变化扩张 Bounds。

可选方案：

### 粗粒度扩张

```ts
const BOUNDS_EXPANSION_STEP = 8;

newMaxX = Math.ceil(requiredMaxX / 8) * 8;
```

这样箭移动八米才更新一次 Bounds。

### 固定保守 Bounds

如果这一批次只有一个 Draw Call，可以直接使用较大的保守范围，避免运行时调用 `onGeometryChanged()`。

### 以玩家为中心进行局部坐标重定位

让批次节点跟随玩家，顶点存储相对坐标，使用固定半径 Bounds。这个结构最好，但改动较大。

第一轮建议先做粗粒度扩张。

---

# 七、辅助瞄准不是主要持续热点

最新增加的垂直辅助瞄准会执行一次长线段候选查询，但它只在真正调用 `launch()` 时执行，而不是蓄力期间每帧执行。

因此它可能带来射箭瞬间的小尖峰，但不应该造成持续 30～40 FPS。

可以后续做：

* 瞄准目标缓存；
* 右摇杆角度变化不大时复用；
* 每 50ms 更新一次目标；
* 将目标选择提前到蓄力阶段。

但优先级明显低于弦网和 Renderer。

# 推荐实施顺序

## P0：立即止血

### 1. 弦网改成 20Hz

预计直接移除约三分之二的弦网查询成本。

### 2. 弦网改用专用简单重叠检测

不再调用带 12 轮二分的 `collectArrowSweepHits()`。

### 3. 胶囊二分临时从 12 降到 4

这是临时方案。四轮误差约为当前线段长度的 `1/16`，对于每帧不足约 1.5 米的箭段通常已足够。

```ts
const INTERSECTION_REFINEMENT_STEPS = 4;
```

长期仍建议替换成解析求交。

### 4. Renderer 停止每帧上传 Color

仅上传 Position。

### 5. Bounds 改成 8 米粒度扩张

避免连续调用 `onGeometryChanged()`。

这批修改风险低，最适合作为第一个性能修复提交。

---

## P1：结构优化

### 1. Crowd 使用 Query Stamp 去重

消除候选缓冲近似 O(n²) 的线性去重。

### 2. 弦网一次宽相位，处理全部边

当前每条边分别执行一次 DDA。

更好的方式是：

1. 计算整个弦网的包围区域；
2. 宽相位收集一次候选怪物；
3. 每个候选最多测试六条边。

这样怪物不会被六次重复加入候选缓冲。

### 3. 投射物改为解析式竖直胶囊求交

分别求：

* 竖直圆柱的二次方程交点；
* 上端球交点；
* 下端球交点；
* 取最小合法 `t`。

彻底移除二分循环。

### 4. Renderer 使用 Dirty Range 和零分配写入

让静态地面箭、未启用槽位和静态弦线不再产生每帧成本。

# 性能验收目标

在约 200～220 个怪物、六支箭、五条弦线全部激活时，建议要求：

```text
Weapon 平均 CPU：不高于改动前基线 + 0.5ms
Weapon 峰值 CPU：低于 2ms
弦网检测频率：不高于 20Hz
单帧胶囊二分次数：0，或临时不超过数百次
静止箭 Position 上传：0 字节
无显隐变化时 Color 上传：0 字节
Bounds 更新：正常战斗中接近 0 次/秒
持续两分钟无明显周期性 GC 尖峰
```

## 最推荐的第一个提交

```text
perf: 降低猎弓弦网查询频率并移除全量箭批次上传
```

这个提交建议包含：

* 弦网检测降为 20Hz；
* 弦网独立简单碰撞；
* 胶囊二分 12 → 4；
* Color 按需上传；
* 隐藏槽不再每帧折叠；
* Bounds 采用粗粒度扩张；
* 新增弓箭性能子阶段。

**我判断最大的收益会来自“弦线不再每帧执行精确投射物胶囊求交”，其次才是动态 Mesh 优化。** 只调箭速、射程、弦线数量或者视觉尺寸无法根治，因为当前问题本质上是查询频率、算法复杂度和无效全量上传叠加。
