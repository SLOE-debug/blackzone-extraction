# 总体结论

我重点检查了 `main` 分支上的装备域、枪械运行时、抓取/投掷模块、HUD 输入、宝箱掉落以及动态网格热路径。这个仓库目前是 **Cocos Creator + 分阶段 World Scheduler + SoA/ECS 风格数据 + 手写动态合批**。仓库本身很适合改造成纯近战，但不能只删几把枪的配置：当前核心装备接口、玩家武器运行时、动画动作、弹药 HUD、投射物阶段和战利品表都带有明显的枪械假设。

最合理的路线是：

1. 先修复宝箱长帧，因为原因已经比较明确，而且与玩法重构相对独立。
2. 把“枪械武器运行时”改成“武器行为运行时”，接入大锤。
3. 用通用的击退、腾空、朝向锁定 ECS Effect 替代抓取/投掷。
4. 切换默认装备和掉落表后，彻底删除枪械、弹药、弹丸、抓取和投掷代码。
5. 最后接入 5 格物品栏与“撤离锁定格”。

# 一、现有代码的关键问题

## 1. 枪械不是一个可以直接拔掉的小模块

当前装备目录注册了沙漠之鹰、霰弹枪、KRISS Vector、M4A1、AKM，以及五种弹药。 当前类型层也把这些枪和弹药写死在 `EquipmentId`、`WeaponEquipmentId`、`AmmunitionEquipmentId` 联合里。

更深层的问题是 `assets/core/equipment/equipment.ts`：

* `WeaponClass` 只有手枪、霰弹枪、冲锋枪、突击步枪。
* `WeaponGrip` 只有手枪和长枪。
* `WeaponAction` 只有 Ready、Fire、Reload。
* `WeaponEquipmentDefinition` 强制要求弹药、射击模式和弹丸参数。

玩家武器运行时也同时拥有弹药库存、装填状态、攻击执行器、实体弹丸人口和枪口姿态；装备武器时会创建弹匣、手持渲染器和弹丸人口。

因此不要把大锤伪装成“无限弹药、零速度弹丸的枪”。那样会留下大量错误抽象。

---

## 2. 抓取/投掷已经独立成模块，但触及范围很广

目前行为模块标识只有：

```text
Grab
Throw
Reserved
```

并且前置条件、行为类型和预览都围绕“是否携带目标”设计。

输入调用链则是：

```text
BattlefieldSkillWheel
    → BattlefieldActionInputWorldSystem
    → BattlefieldCombatModuleRuntime
    → Grab / Throw Module
    → Monster Manipulation Registry
```

技能输入会记忆世界方向、处理死区，并在技能手势期间关闭枪械开火。

最近提交还刚刚为抓投增加了目标锁定、触摸取消、三维携带锚点和怪物操作状态，说明这些功能虽然新，但模块边界清楚；此时整体删除反而比继续维护两套战斗范式更合适。

# 二、建议的目标战斗架构

不要再让“武器”直接决定弹丸、弹药和射击，而是使用武器行为：

```text
输入
  ↓
WeaponCommandBuffer
  ↓
WeaponActionSystem
  ↓
HitQuery / CombatEventBuffer
  ↓
DamageEffect
KnockbackEffect
VerticalLaunchEffect
FacingLockEffect
  ↓
Movement / Crowd / Airborne Simulation
  ↓
Animation / Rendering / HUD
```

建议核心类型调整为：

```ts
export enum WeaponKind {
  Sledgehammer = 'sledgehammer',
}

export enum WeaponGrip {
  OneHandHeavy = 'one-hand-heavy',
}

export enum WeaponAction {
  Idle = 'idle',
  WindupLeft = 'windup-left',
  SwingLeft = 'swing-left',
  WindupRight = 'windup-right',
  SwingRight = 'swing-right',
  Uppercut = 'uppercut',
  Spin = 'spin',
  Recover = 'recover',
}

export interface MeleeWeaponDefinition<TId extends string> {
  readonly id: TId;
  readonly displayName: string;
  readonly baseDamage: number;
  readonly reach: number;
  readonly hitArcRadians: number;
  readonly attackIntervalSeconds: number;
  readonly knockbackImpulse: number;
  readonly comboWindowSeconds: number;
  readonly specialRequiredHits: number;
}
```

大锤自己的可升级参数不要塞进通用武器定义，可以单独配置：

```ts
export interface SledgehammerProgressionStats {
  /** 策划直接理解的目标高度，而不是初速度。 */
  readonly uppercutLaunchHeight: number;
  readonly spinDurationSeconds: number; // clamp 到 2–3 秒
  readonly spinKnockbackImpulse: number;
  readonly spinPulseIntervalSeconds: number;
}
```

向上挑时再把目标高度换算成初速度：

```ts
launchVelocityY = Math.sqrt(2 * gravity * uppercutLaunchHeight);
```

这样升级显示“击飞高度 +20%”时，策划数值和实际视觉高度是一致的。

# 三、大锤完整玩法方案

## 1. 手持姿态

当前 `HeldWeaponProfile` 是围绕 `WeaponAimRoot` 和枪口偏移设计的。 建议改成更中立的 `HeldEquipmentProfile`，删除 muzzle 字段，由武器行为自行扩展。

大锤待机姿态：

* 右手单手握住锤柄上半段。
* 手臂自然下垂，肘部略微弯曲。
* 锤柄向前下方倾斜。
* 锤头靠近右脚外侧地面。
* 移动时锤头有轻微惯性拖曳，而不是和手完全刚性同步。

不要用刚体吊锤头。用动画姿态计算即可：

```text
RightHandSocket
  → HammerGripRoot
      → HammerMesh
```

待机时根据角色脚底高度计算一个 `hammerHeadGroundTarget`，再由手部位置和地面目标求锤柄方向；攻击动作期间切换为预制曲线。

---

## 2. 普通挥动

右摇杆改成“攻击方向摇杆”：

* 向右拨：右侧起手，向左横扫。
* 向左拨：左侧起手，向右横扫。
* 摇杆方向同时确定人物朝向。
* 连续按同一侧时，可自动交替挥动，避免玩家必须机械左右拨动。

命中不应使用锤头单点碰撞，而应使用一段随动画扫过的 **胶囊/扇形扫掠体**：

```text
上一帧锤头位置
    ╲
     ╲  Swept Capsule
      ╲
本帧锤头位置
```

每次攻击生成递增的 `attackSequenceId`，怪物保存最近命中的序列号，保证同一次挥动不会在多个帧中重复结算。

命中效果：

```ts
DamageEffect
PlanarKnockbackEffect
HitStopEffect        // 玩家侧极短顿帧，怪物模拟不暂停
HitFlashEffect
HammerComboHitEvent
```

怪物击退最好作为通用 ECS 效果：

```ts
interface PlanarKnockbackEffect {
  directionX: number;
  directionZ: number;
  initialSpeed: number;
  remainingSeconds: number;
  resistanceScale: number;
}
```

这样大锤、怪物技能、爆炸、敌人互撞以后都能复用。

---

## 3. 连续命中 5 下

只统计“确认命中怪物”的攻击，不统计空挥。建议规则：

```text
命中 → hitCount + 1，刷新 2.5 秒连击窗口
空挥 → 不立刻清零，但不刷新窗口
超时 / 受控倒地 / 使用特殊技 → 清零
达到 5 → 获得一层「震势」
```

HUD 在技能键周围显示 5 段充能环。

## 4. 两种特殊方式

我建议把一个技能按键做成长短按分支，这样不需要再添加第二个按钮。

### 短按：升龙震击

* 消耗一层“震势”。
* 向当前朝向执行从下向上的锤击。
* 前方窄扇形目标受到伤害和垂直腾空。
* `uppercutLaunchHeight` 是可升级变量。
* 大型或精英怪通过 `AirborneResistance` 降低高度，而不是完全免疫。

执行链：

```text
SkillButton TOUCH_END（短按）
  → RequestUppercut
  → HammerActionSystem.startUppercut
  → HammerUppercutHitSystem
  → DamageEvent
  → VerticalLaunchEffect
  → AirborneIntegrationSystem
  → LandingSystem
```

不要保留原抓投系统里的 `manipulation.elevation` 作为通用击飞实现。应新建通用组件：

```ts
AirborneMotion {
  elevation;
  velocityY;
  gravityScale;
  groundHeight;
}
```

### 长按：地磁风暴

这是我推荐的大锤专属技能：

* 长按技能键 0.35 秒触发。
* 消耗一层“震势”。
* 持续 2.6 秒，可升级到最多 3 秒。
* 开始瞬间锁定人物朝向。
* 每隔约 0.32 秒对周围敌人造成一次低伤害和径向击退。
* 最后一圈产生更强冲击波。
* 被命中的敌人附加 2 秒 `Magnetized`：

  * 两个带有该效果的敌人互撞时产生一次小型二次冲击。
  * 每对实体在一次技能中最多触发一次，防止指数级连锁。

这能充分发挥“任何 Entity 都可附加任意效果”的 ECS 优势，而不是单纯做普通范围伤害。

旋转调用链：

```text
SkillButton HOLD
  → BattlefieldWeaponInputWorldSystem
  → HammerCommandBuffer.requestSpin
  → HammerActionSystem.startSpin
      → add FacingLockEffect
      → add SpinAttackEffect
  → HammerSpinSystem.queryNearby
      → DamageEvent
      → PlanarKnockbackEffect
      → MagnetizedEffect
  → KnockbackSystem
  → Crowd / MonsterMovement
  → HammerActionSystem.finishSpin
      → remove FacingLockEffect
```

### 左摇杆朝向锁定的正确实现

不能只在大锤系统里“不读取左摇杆”，因为人物移动系统可能早已更新了 heading。

应在输入之后、移动朝向求解之前写入：

```ts
FacingLockEffect {
  lockedHeading: number;
  remainingSeconds: number;
  source: FacingLockSource.HammerSpin;
}
```

人物朝向系统：

```ts
if (facingLock.active) {
  heading = facingLock.lockedHeading;
} else {
  heading = resolveHeadingFromMovementAndAttackInput();
}
```

锁定必须在旋转开始的同一 `ActionExecution` 阶段生效，确保第一帧旋转就不会被左摇杆改向。移动可以保留，但建议移动速度降到 30%–40%；仅锁朝向，不必完全禁用位移。

# 四、右侧操作区改造

当前 HUD 同时持有移动摇杆、瞄准摇杆和独立 `BattlefieldSkillWheel`。 技能轮盘自身还创建了前一个、当前、后一个三个命中节点。

建议删除三槽轮盘，重构为：

```text
右侧攻击摇杆
┌────────────────┐
│        [技能键] │  ← 固定在摇杆环内部右上方
│       ╭────╮   │
│       │ 摇杆 │   │
│       ╰────╯   │
└────────────────┘
```

交互规则：

* 摇杆区域拖动：确定朝向和普通攻击。
* 技能键：短按升龙、长按旋转。
* 技能键拥有独立 touch ID，并阻止事件继续传给摇杆。
* 多点触控时，左摇杆、右摇杆、技能键分别持有自己的触点。
* 接近宝箱或物品时，右摇杆中心显示“开启/拾取”提示；轻点中心触发场景交互。
* 技能键始终在摇杆圆环右上方，不与场景交互图标互相替换。

当前代码已经把宝箱开启/装备拾取图标写入 `aimJoystick`，并在出现交互时清除瞄准状态。 因此可以保留这部分“中心交互”，只删除上方独立技能轮盘。

建议保留并重命名现有 `BattlefieldSkillGesture` 的触摸所有权和 `TOUCH_CANCEL` 逻辑，例如改为：

```text
ExclusiveActionGesture
```

它对长按技能和移动端多指操作仍然很有价值。

当前玩家实际上只有一个武器槽；拾取世界装备后会直接进入 `receive()`，武器立即替换，弹药立即进入备用库存。

# 七、宝箱打开卡顿的根因

## 当前调用树

```text
BattlefieldInteractionResolver.activateCurrent
  → BattlefieldTreasurePopulation.activateInteraction
    → TreasureChestRuntime.open
      → rollLoot
      → sessionState.open
      → phase = Opening

随后达到 lootReleaseTime：
BattlefieldTreasurePopulation.update
  → TreasureChestRuntime.update
    → releaseLoot
      → createLootScatterTrajectories
      → DroppedEquipmentPopulation.spawnBurst
        → rebuildRenderer
          ├─ new DroppedEquipmentRenderer
          │   → createDroppedEquipmentBatchGeometry
          │   → write all item poses
          │   → DynamicMeshBatch.initialize
          │       → createDynamicMesh
          │       → new Node
          │       → add MeshRenderer
          │       → GPU buffer initialization
          └─ new DroppedEquipmentAccentRenderer
              → new Material
              → new geometry
              → DynamicMeshBatch.initialize
        → dispose old renderers
```

`open()` 本身只做随机种子、战利品抽取和会话状态写入。 真正昂贵的操作发生在动画达到掉落释放时间后：`releaseLoot()` 调用 `spawnBurst()`。

`spawnBurst()` 每增加一批物品都会同步调用 `rebuildRenderer()`。 而 `rebuildRenderer()` 会新建两个完整渲染器，再销毁旧渲染器。

身体渲染器构造期间会：

* 遍历所有掉落物获得源几何。
* 分配一整套新的合批几何。
* 重写所有姿态。
* 重新计算 bounds。
* 初始化新的动态 Mesh。

合批几何会重新分配 Position、Color、Index TypedArray，并复制全部源索引与颜色流。

强调光柱渲染器还会为每次重建创建新材质、新几何和新动态批次。

最终 `DynamicMeshBatch.initialize()` 会调用 Cocos 的 `createDynamicMesh`，创建 Node、MeshRenderer、Mesh 与 GPU 缓冲，并触发 `onGeometryChanged()`。

这正是移动设备上典型的单帧尖峰来源：

```text
大量 JS 分配
+ TypedArray 拷贝
+ Mesh/Node/Material 创建
+ GPU Buffer 创建和上传
+ 旧资源销毁
+ 后续 GC
```

所以这不是箱盖动画的问题，主因几乎可以确定是 **掉落释放时整批渲染器重建**。

# 八、宝箱修复方案

## P0：最低风险热修

让 `DroppedEquipmentPopulation` 在战场加载阶段预先创建固定容量批次，例如 16 个掉落槽：

```text
DroppedEquipmentBodyPool    capacity = 16
DroppedEquipmentAccentPool  capacity = 16
```

开箱时：

* 从 free list 取槽位。
* 写新槽位的姿态。
* 只上传对应顶点范围。
* 修改 active index count。
* 不创建 Node、MeshRenderer、Material。
* 不销毁旧批次。

已有 `DynamicMeshBatch` 支持上传连续顶点区段和调整实际索引数，可以直接作为实现基础。

## P1：完整容量管理

使用几何容量桶：

```text
8 slots
16 slots
32 slots
64 slots
```

只有超过容量时才在非关键帧扩容。更好的做法是根据活动 Chunk 最大宝箱数和单箱最大掉落数量，在加载阶段直接算出合理上限。

删除物品时：

```text
slot.active = false
freeList.push(slotIndex)
```

不要立即压缩和重建。只有在 Chunk 切换、加载画面或空闲预算中进行整理。

## P1：减少每帧上传

目前身体和光柱渲染器每帧都会遍历全部物品、重算 bounds 并上传整个位置流；光柱还会每帧上传颜色。

应改为：

* Color 只在槽位创建或品质变化时上传。
* 已落地且静止的物品不再更新位置。
* 飞行物只上传对应顶点区段。
* bounds 使用物品位置与预计算包围半径，不扫描全部模型顶点。
* 使用保守世界 AABB 时，可以数帧更新一次，而不是每帧更新。

## P2：预热

在 `completeInitialRendering()` 阶段：

* 创建掉落物 body/accent 批次。
* 初始化材质。
* 访问全部可能掉落的 prototype 几何。
* 触发一次不可见上传。
* 预热 shader variant。

当前宝箱人口已经有加载阶段的 `completeInitialRendering()` 接口，很适合把掉落池预热并入这里。

## 性能验收标准

移动端开箱测试至少覆盖：

```text
已有 0 / 8 / 16 / 32 个地面掉落物
单箱掉落 1 / 3 / 最大数量
连续开启多个相邻宝箱
Chunk 切换后恢复已开宝箱
低端 Android 真机
```

关键断言：

