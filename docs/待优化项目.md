# 一、静止状态为什么还是双手握锤

## 根因一：副手权重只看“有没有装备”，不看“是否正在攻击”

当前代码这样计算握持权重：

```ts
const ready = weaponPose === VanguardWeaponPose.TwoHandHeavy;

mainGripWeight  → ready ? 1 : 0
supportGripWeight → ready ? 1 : 0
```

也就是说，只要装备大锤，即使动作是 `Idle`，左手副握点也会缓动到 100%。

这与需求冲突：

```text
静止、走路：
  右手单手提锤
  左手正常摆动或自然放松

蓄力、挥动、技能：
  左手抓上副握点
  双手共同发力

恢复后半段：
  左手松开
  回到单手提锤
```

## 根因二：`supportGripWeight` 并不是真正的“左手握持权重”

当前求解器先根据 `supportGripWeight` 混合**锤杆方向**，然后无论权重是多少，都对左臂执行完整 Two-Bone IK：

```text
计算 supportX/Y/Z
→ solveArm(左臂, supportX/Y/Z)
→ 始终写入 LeftUpperArm / LeftForearm / LeftHand
```

因此，即便简单把 Idle 的 `supportGripWeight` 改成零，左手也不会真正恢复自然姿势。它仍会被拉向“主握点附近的一段锤柄”。

正确混合应发生在**左手目标位置**上：

```ts
const constrainedSupport = mainGrip + shaft * gripSpacing;

const leftHandTarget = lerp3(
  naturalLeftHandSocket,
  constrainedSupport,
  supportGripWeight,
);
```

然后再对这个混合目标求 IK。

这样：

* 权重为 `0`：左臂保持自然动作；
* 权重为 `0.5`：左手正伸向锤柄；
* 权重为 `1`：左手完全贴合副握点。

# 二、为什么两个胳膊向身体内部凹

这是当前握点布局导致的，不只是肘部参数问题。

角色肩膀分别位于局部 X 轴约 `-0.68` 和 `+0.68`。

但普通横扫期间，主握点几乎固定在：

```ts
x = 0.18
y = 2.48
z = 0.42
```

大锤主副握点的角色空间距离又只有 `0.3375`。

这导致两个手掌都集中在胸口中央附近：

```text
左肩 x ≈ -0.68
左手目标 x ≈ 0.0～0.4

右肩 x ≈ +0.68
右手目标 x ≈ 0.18
```

特别是左臂，要从身体左侧跨过胸口去够右侧的锤柄，所以截图中会出现：

* 左前臂插向胸腹中央；
* 左肘向身体内部收；
* 两手重叠；
* 从侧面看，手臂与身体几乎融为一块。

当前肘部 Pole 的默认位置虽然位于身体两侧，但前向分量只有 `z = 0.72`，并不足以把肘部明确撑到身体外侧。

## 正确原则

挥锤时，手不是固定在胸前一点，然后让锤子绕手旋转。

应当是：

```text
肩膀和胸腔转动
  ↓
两只手整体向身体前方送出
  ↓
握点中心随挥动方向横向移动
  ↓
锤头在人物前方划弧
  ↓
肘部留在身体左右外侧
```

两肘应形成明显的外扩轮廓：

```text
左肘  ←  左手  锤柄  右手  →  右肘
             身体前方
```

而不是：

```text
左肘 → 左手右手 ← 右肘
          胸腔内部
```

# 三、普通挥动为什么像向地面砸

## 当前轨迹以“下垂姿态”为中心

普通待机锤杆方向是：

```ts
neutral = {
  x: 0,
  y: -0.96,
  z: 0.28,
}
```

也就是强烈向下，仅略微朝前。

左右蓄力都从这个向下方向开始，恢复阶段又回到这个向下方向。

左右横扫虽然把锤杆逐渐变为接近水平，但整个动画只有一条“锤杆方向曲线”，没有独立的：

* 两手中心轨迹；
* 锤头世界轨迹；
* 接触点高度；
* 身体前方距离；
* 肩膀前送量。

普通攻击的主握点在整个左右横扫中基本不动，只有上挑、重砸和旋风才稍微调整它。

结果就是：

> 手固定在胸口附近，长锤从下垂状态被旋转到另一侧。

即使数学上锤杆在挥击阶段接近水平，视觉上也仍像“从地面附近抡起来再落下去”，而不是把锤头送到身体前方扫过敌人。

# 四、普通横扫不能再只定义“锤杆方向”

应把目前的：

```ts
writeVanguardTwoHandShaftDirection(...)
getVanguardTwoHandMainGripAxis(...)
```

重构成一套完整的动作轨迹输出：

```ts
interface HammerAttackTrajectoryPose {
  mainGripX: number;
  mainGripY: number;
  mainGripZ: number;

  shaftX: number;
  shaftY: number;
  shaftZ: number;

  chestYaw: number;
  pelvisYaw: number;

  leftElbowPoleX: number;
  leftElbowPoleY: number;
  leftElbowPoleZ: number;

  rightElbowPoleX: number;
  rightElbowPoleY: number;
  rightElbowPoleZ: number;

  supportGripWeight: number;
}
```

更理想的是直接输出：

```text
主握点目标
副握点目标
锤头目标
```

再由这三个点反解锤子和手臂。

## 普通横扫关键帧

### 1. Idle：单手自然下垂

```text
右手：角色右髋外侧
左手：自然放松
锤头：右脚外侧附近，略高于地面
锤柄：向下、稍向外倾斜
```

右手目标不应该位于 `x=0.18` 的胸前中心，建议移动到角色右侧：

```ts
idleMainGrip ≈ {
  x: 0.50～0.62,
  y: 1.55～1.75,
  z: 0.18～0.32,
}
```

锤头与地面保留少量间距，避免穿地。

### 2. Windup：左手抓上锤柄

蓄力前 30% 左手完成握持：

```ts
supportGripWeight =
  smoothstep(0, 0.3, progress);
```

此时两手中心开始向前移动，不能继续停留在胸腔中央。

### 3. Swing：身体前方横扫

普通挥动的接触窗口应满足：

```text
锤头高度：
  始终高于骨盆或大腿上部

锤头前向距离：
  明显位于身体前方

双手：
  同时位于胸腹前方

双肘：
  始终在身体左右外侧
```

建议用三次 Bézier 或 Hermite 曲线直接描述锤头：

```text
起点：身体一侧稍后方
控制点 1：身体侧前方
控制点 2：正前方最远点
终点：身体另一侧前方
```

概念轨迹：

```text
            接触区
          ┌────────┐
蓄力 ●────┘  玩家  └────● 随挥
             ↑
          身体正前方
```

而不是现在这种：

```text
地面下垂
   ↓
绕胸口固定点翻转
   ↓
回到地面下垂
```

### 4. Recover：先随挥，再松开左手

左手不能在命中后立刻放开。建议：

```text
Recover 0%～65%：
  双手继续控制随挥和减速

Recover 65%～100%：
  左手松开
  右手把大锤自然带回右侧下垂
```

# 五、目前所谓的“丝滑 SoA”仍只解决了一半

最新提交确实增加了这些连续 SoA 字段：

* 胸腔偏航及速度；
* 左右肘部 Pole；
* 主副握点权重；
* 锤体滞后及速度。

但现在的连续性主要是对若干目标参数进行 `damp` 或临界阻尼，底层动作目标仍是离散函数。

现有测试只验证了：

* 双手贴合握点；

* 肘部角度大于一个很低的阈值；

* 左右横扫的位置连续；

* 胸腔不会过度旋转。

它们没有验证：

* Idle 必须单手；
* 左手是否穿过胸腔；
* 两肘是否位于身体外侧；
* 普通挥动的锤头是否始终高于地面；
* 接触瞬间是否位于人物正前方；
* Windup/Swing 边界的速度是否连续；
* 屏幕投影后的姿势是否自然。

现有“轨迹连续”测试只比较阶段边界的方向值相等，属于 **C0 位置连续**，没有检查速度和加速度。真正丝滑至少应检查 C1 速度连续。

# 六、正确的动态握持状态

`TwoHandHeavy` 应表示：

> 这种武器支持双手重攻击。

不应表示：

> 只要装备这种武器，永远双手粘在锤柄上。

建议增加明确的握持状态：

```ts
enum WeaponGripEngagement {
  MainHandOnly,
  ReachingSupportGrip,
  TwoHandLocked,
  ReleasingSupportGrip,
}
```

或者继续使用无分支的 SoA 权重，但目标必须由动作阶段决定：

```ts
function getSupportGripTarget(
  action: VanguardWeaponAction,
  progress: number,
): number {
  switch (action) {
    case Idle:
      return 0;

    case WindupLeft:
    case WindupRight:
      return smoothstep(0, 0.32, progress);

    case SwingLeft:
    case SwingRight:
    case Uppercut:
    case GroundSlam:
    case Spin:
      return 1;

    case Recover:
      return 1 - smoothstep(0.65, 1, progress);
  }
}
```

对应调用链：

```text
HammerActionState
  → action / progress
  → WeaponAnimationState
      → supportGripTarget
      → 平滑 supportGripWeight
  → TwoHandHeavyPose
      → 混合左手自然目标与副握点目标
      → 双臂 IK
  → WeaponRoot
  → 锤头世界位置
  → Swept Capsule
```

当前真实锤头已经用于连续扫掠，这一部分可以保留；应改变的是产生锤头姿态的动画轨迹，而不是重新引入独立战斗轨迹。

# 七、右侧摇杆当前确实仍在指定攻击方向

现在 HUD 状态明确包含：

```ts
attackX
attackY
attacking
```

并且右侧控制仍然是完整的 `VirtualJoystick`。

每帧会读取右摇杆向量并归一化为攻击方向。

随后输入系统把这个屏幕向量转换成世界方向，再调用：

```ts
weapon.commands.requestSwing(
  attackDirection.x,
  attackDirection.z,
  ...
);
```

这与现在的新需求不一致。

## 正确控制形式

右侧不应继续显示为“可拖动摇杆”，否则玩家会自然理解为可以控制方向。

应改成：

```text
右侧中央：普通攻击按钮
左侧/左上/上方：三个独立技能按钮
附近有宝箱或掉落物时：
  普攻按钮临时显示开启/拾取图标
```

输入状态改为：

```ts
interface BattlefieldScreenControlState {
  moveX: number;
  moveY: number;

  attackPressed: boolean;
  attackHeld: boolean;

  cameraOrbitDeltaX: number;
}
```

彻底删除：

```ts
attackX
attackY
```

桌面端也不再使用方向键或 I/J/K/L 指定攻击方向，而是使用一个普通攻击键。

# 八、近战自动朝向规则

这类大锤更适合 ARPG/MOBA 的近战辅助瞄准：

```text
按下普通攻击
  ↓
附近是否有可攻击单位？
  ├─ 有：直接朝目标方向挥动
  └─ 无：
      左摇杆是否有移动输入？
        ├─ 有：沿左摇杆移动方向挥动
        └─ 无：沿最后移动方向或当前人物朝向挥动
```

## 推荐优先级

### 第一优先级：附近单位

普通攻击触发时，在玩家附近搜索可攻击单位：

```ts
autoTargetRadius = weaponReach + 1.0～1.5;
```

当前大锤射程为 `3.9`，因此自动锁敌半径可以先采用约 `5.0`。

选中后：

```ts
directionX = normalize(targetX - playerX);
directionZ = normalize(targetZ - playerZ);
```

动作状态已经会在 `requestSwing()` 时保存方向并锁定朝向，因此只需要替换方向来源，不需要重写整个攻击状态机。

### 第二优先级：左侧移动方向

没有附近目标时，读取：

```ts
controls.moveX
controls.moveY
```

通过相机方向转换为世界移动方向，然后用于挥动。

### 第三优先级：最后有效移动方向

玩家站立不动并点击攻击时，使用：

```text
最近一次非零左摇杆方向
```

没有历史方向时，再使用角色当前朝向。

# 九、自动锁敌可以直接复用现有空间索引

目前 `BattlefieldMonsterTargetRegistry` 已经拥有：

* 预分配候选缓冲；

* Crowd 圆形范围查询；

* 不同怪物群的统一位置读取；

* 生命周期数组；

* 群体与实体稳定 ID。

怪物 Crowd 视图也已经暴露 `lifecycle`、`participation` 和位置 SoA。

因此不应遍历全部怪物，更不需要新增物理碰撞查询。只需增加：

```ts
interface MutableMeleeTarget {
  populationId: number;
  entityId: number;
  x: number;
  z: number;
  distanceSquared: number;
}

writeBestMeleeTarget(
  originX: number,
  originZ: number,
  radius: number,
  preferredPopulationId: number,
  preferredEntityId: number,
  result: MutableMeleeTarget,
): boolean;
```

内部继续使用：

```ts
crowd.collectCircleCandidates(...)
```

并过滤：

```text
lifecycle === Alive
participation !== 0
距离在锁敌半径内
```

## 目标稳定性

不能每帧重新选择最近怪物，否则多人包围时人物会左右抽搐。

正确方式：

```text
一次攻击开始前：
  选择目标
  锁定攻击朝向

Windup / Swing / Recover：
  不再改目标

下一次攻击：
  重新评估
```

连续攻击时可以保留当前目标，直到：

* 目标死亡；
* 超出扩展锁定半径；
* 目标被移除；
* 玩家停止攻击。

建议使用约 `1.2～1.3` 倍的释放半径形成迟滞，防止目标在边缘来回切换。

# 十、技能方向也应统一

普通横扫取消右摇杆方向后，技能也不应偷偷继续依赖旧攻击方向。

建议：

* **冲天上挑**：优先自动锁定附近目标，否则使用左摇杆方向。
* **裂地重砸**：优先目标，否则使用左摇杆或当前朝向。
* **旋风**：不需要目标方向，只在开始时使用当前角色朝向。

技能开始后仍锁定本次动作的方向，不能在技能执行中持续跟随目标。

# 十三、新的验收测试

现有测试中“装备双手武器后同时约束左右臂”的断言需要改掉，因为它正在固化错误的 Idle 设计。

新的验收应包括：

1. Idle 时右手贴合主握点，左手接近自然姿态，而不是贴合副握点。
2. Windup 结束前，左手必须平滑贴合副握点。
3. Swing 接触阶段两只手都位于角色身体前方。
4. 普通 Swing 接触窗口的锤头高度不得接近地面；只有 `GroundSlam` 可以向地面运动。
5. 左肘始终位于身体左侧外部，右肘始终位于身体右侧外部。
6. 手臂线段不得穿过胸腔碰撞胶囊。
7. Windup、Swing、Recover 边界的位置和速度都连续。
8. 右侧输入方向变化不得改变普通攻击方向。
9. 附近存在怪物时，角色朝向怪物。
10. 无怪物时，攻击方向等于左侧移动方向。
11. 静止无目标时，使用最后移动方向。
12. 一次挥动中不得重新切换目标。
