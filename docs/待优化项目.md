我查看的是当前最新提交 `597ebdb9`：**“实现抓取与投掷行为模块第一版”**。整体 ECS 拆分方向没有问题，但这三个现象确实都能从代码中找到原因。

核心问题可以概括为：

> **抓取使用瞬时二维方向查询，投掷使用三维轨迹，而 Crowd 仍然只认识二维平面。**

三个系统对“方向、高度、实体是否还参与怪群”的理解没有统一。

---

## 1. 抓取箭头确实只是一个丑陋的 UI 箭头

当前抓取预览不是地面技能指示器，而是：

1. 从玩家 `Y + 0.8` 到前方 `3.8` 米写一条世界线段；
2. 投影到 UI Canvas；
3. 使用 `Graphics.lineTo()` 画直线；
4. 末尾补一个三角形箭头；
5. 找到目标后，在怪物头顶画圆圈和折线。

所以它必然看起来像调试射线，而不是技能。

### 应该怎么改

抓取预览应该拆成两个表现层：

**地面技能指示器**

* 从玩家脚底出现；
* 贴着地面向目标方向延伸；
* 使用半透明蓝色扇形、楔形或符文轨道；
* 外沿表示最大距离；
* 中间用流动纹路表现抓取方向；
* 有目标时，指示器尖端轻微吸向目标。

大概是：

```text
   玩家脚下
      ◉
     ╱ ╲
    ╱  蓝色符文区域
   ╱──────▶
```

**怪物头顶标记**

继续使用屏幕空间 Billboard/UI 标记即可，但应该设计成“可抓取/已锁定”的技能图标，而不是圆圈加屋顶形折线。

不要继续让 `BattlefieldActionPreviewHud` 同时承担地面范围和头顶标记。建议拆为：

```text
BattlefieldActionGroundPreviewRenderer
BattlefieldActionTargetMarkerHud
```

前者使用世界空间低多边形 Mesh 或动态几何，后者才使用 UI 投影。

## 2. 投掷并不是完全没算 Y，而是只算了一半

### 已经计算 Y 的部分

投掷飞行确实有三维高度：

* 起始高度来自携带怪物的 `startY`；
* 使用低弧线公式计算每帧 `y`；
* 速度包含 `velocityY`；
* 扫掠碰撞查询包含 `startY/endY`；
* 碰撞强度也包含纵向速度。

所以实际投掷和窄相位碰撞并非纯二维。

### 没有计算 Y 的部分

投掷落点的障碍检查完全是 XZ 平面：

```ts
movement.resolve(lastX, lastZ, targetX, targetZ, radius, result);
```

它不知道怪物是贴地飞、越过矮墙，还是在三米高的空中。

更严重的是 **Crowd Separation 完全没有高度字段**。它只有平面 `x/y`、半径和逆质量。

Crowd 重建时会把所有处于 `Alive` 生命周期的怪物加入二维空间哈希，根本不检查怪物当前是 `Free`、`Carried` 还是 `Thrown`。

而抓取发生后，代码只是：

```ts
crowdPopulation.inverseMass[entityId] = 0;
```

这并不是把怪物移出 Crowd，而是把它变成一个**质量无限大的二维障碍物**。

Crowd 求解时，逆质量为零的一方完全不移动，另一方承担全部分离修正。因此底下怪物真的会给空中怪物让路。

### 正确修法

不要用 `inverseMass = 0` 表示“不参与 Crowd”。

给 `PlanarCrowdPopulation` 增加明确的参与状态：

```ts
readonly active: Uint8Array;
// 或
readonly participation: Uint8Array;
```

Crowd 重建时：

```ts
if (lifecycle !== Alive || participation[index] === 0) {
  continue;
}
```

状态规则：

```text
Free
→ 参与 Crowd

Carried
→ 不参与 Crowd

Thrown
→ 不参与 Crowd

投掷落地且未死亡
→ 重新寻找合法落脚点
→ 恢复参与 Crowd
```

同时不要在恢复时硬编码 `inverseMass = 1`。目前释放和击杀都会直接恢复成 1，这会破坏未来不同体型怪物原本的质量配置。

更长期的设计应该分开三种资格：

```text
crowdEnabled
targetingEnabled
projectileCollisionEnabled
```

一只被投掷的怪物可以：

* 不参与 Crowd；
* 不作为普通枪械目标；
* 但作为投掷物继续与其他怪物发生三维碰撞。

## 3. “显示可抓取但抓不到”的 Bug 确实存在

`beginCarry()` 本身并没有要求角色身体正对怪物。

真正要求方向的是前面的 `findGrabbable()`：

```ts
alignment >= minimumDirectionAlignment
```

而抓取方向的来源是：

```text
技能按钮有拖动方向
→ 使用技能按钮方向

否则右摇杆正在瞄准
→ 使用右摇杆方向

否则
→ 使用玩家当前 heading
```

所以没有拖动技能按钮、也没有持续操作右摇杆时，确实会退化为“角色必须面朝怪物”。

而且当前筛选同时设置：

* 最大距离 `3.8`；
* 横向宽度 `1.35`；
* 对齐角约 `41.4°`。

在最远的 `3.8` 米处，横向宽度实际上把有效角度压缩到了大约 **±21°**。所以远处怪物需要非常接近正前方，确实很容易产生“必须正对”的感觉。

### 更明确的输入 Bug

技能按钮没有有效的方向 Dead Zone。

触摸点只要和按钮中心存在极小偏移，就会被归一化成一个完整方向；世界输入系统又把任何大于 `0.000001` 的幅度都认为是有效技能方向。

这意味着：

```text
手指在按钮中心轻微抖动
→ 产生随机方向
→ 覆盖右摇杆方向和角色朝向
```

### 为什么标记出现了，松手却抓不到

抓取过程中每一帧都会重新搜索目标；松手时也会重新查询一次，没有保存预览阶段锁定的目标。

因此可能发生：

```text
上一帧：
方向正确
→ 找到目标
→ 显示头顶标记

松手帧：
手指位置轻微变化
→ 方向发生变化
→ 重新查询失败
→ GrabCancelled
```

也可能是怪物在这两帧之间移动、死亡或离开范围。

当前测试完全没有覆盖这种情况：测试中的按住和松开使用完全相同的固定方向，而且假的怪物网关根本不读取查询方向。

## 抓取应该改成“锁定会话”

按住抓取时建立一个 `GrabTargetLock`：

```ts
interface GrabTargetLock {
  active: boolean;
  populationId: number;
  entityId: number;
  lastValidX: number;
  lastValidY: number;
  lastValidZ: number;
}
```

行为应该是：

```text
按住技能
→ 搜索目标
→ 找到后锁定实体身份
→ 显示头顶锁定标记

继续按住
→ 优先验证同一个目标
→ 不因轻微方向变化立刻切换

松开
→ 对锁定目标做最终验证
→ 执行抓取
```

最终验证只检查：

* 目标仍存活；
* 仍处于可抓取状态；
* 距离没有严重超出；
* 路径没有被真正阻挡。

不应该在松手时重新从零选择目标。

建议加入滞后范围：

```text
获取目标角度：约 35°
保持锁定角度：约 55°

获取最大距离：3.8
保持最大距离：4.1
```

这样锁定不会在边界疯狂闪烁。

输入层则需要：

```text
技能拖动幅度 < 0.18
→ 认为没有技能方向
→ 使用最后有效瞄准方向

技能拖动幅度 ≥ 0.18
→ 才使用技能按钮方向
```

最好保存 `lastCombatAimDirection`，不要默认依赖玩家身体朝向。这样角色正在移动或转身时，抓取仍然符合玩家刚才的瞄准意图。

## 建议修复顺序

### P0：先解决实际 Bug

1. 为 Crowd 增加参与掩码，携带和投掷时彻底移出 Crowd。
2. 抓取按钮增加方向 Dead Zone。
3. 抓取预览锁定实体，松手不再重新从零选目标。
4. 增加“目标标记出现后，轻微滑动松手仍能抓取”的自动化测试。
5. 增加“空中投掷物经过怪群上方时，地面怪物位置不发生 Crowd 修正”的测试。

### P1：重做表现

1. 删除当前屏幕空间长箭头。
2. 新增玩家脚下的世界空间蓝色技能范围。
3. 把目标头顶标志拆成独立 HUD。
4. 投掷轨迹继续保留三维弧线，但落点和障碍预测需要逐步接入高度信息。

## 总结

你的三个观察都对：

* **抓取箭头丑**：因为它确实只是把一条调试线投影到 UI。
* **空中怪物让地面怪物让路**：因为被投掷实体仍在二维 Crowd 中，并被设置成不可移动障碍。
* **显示目标却抓不到**：因为方向输入过于敏感，而且预览目标没有被锁定，松手时会重新查询。

这不是三个孤立的小 Bug，而是第一版里**世界空间表现、三维投掷和二维 Crowd 资格管理尚未真正分层**。修正这三个边界后，现有模块架构本身可以继续保留。

以上是对最新提交的静态代码分析；我没有在 Cocos 编辑器或真机触摸环境中实际复现。
