# 大锤 2+1 连段、旋风无敌与手机开箱性能重构

## 一、任务目标

基于当前 `main` 最新提交继续开发，不回退现有大锤智能朝向与怪群方向规划。

本次完成五项改动：

1. 大锤连续执行两段普通横扫后，下一段连击自动变成群体上挑；
2. 上挑不再是主动技能，技能区只保留旋风和裂地重砸；
3. 两枚技能按钮沿现有右侧圆弧等距、对称排列；
4. 旋风期间免疫所有敌方攻击，并允许重复命中持续累积怪物击退速度；
5. 彻底消除手机打开宝箱时的单帧卡顿。

---

# 二、确定的产品规则

## 2.1 大锤攻击节奏

普通攻击循环固定为：

```text
第一段：普通横扫
第二段：普通横扫
第三段：自动群体上挑
然后重新开始
```

即：

```text
横扫 → 横扫 → 上挑 → 横扫 → 横扫 → 上挑
```

这里按照“连段段位”计数，不按照命中的怪物数量计数。

一锤同时命中十只怪，仍然只算一段攻击。

上挑不再需要单独按键，也不消耗震势资源。

## 2.2 连段中断规则

以下情况重置 2+1 连段段位：

```text
玩家松开攻击并结束当前动作；
连段超时；
玩家死亡；
卸下或切换武器；
旋风或裂地重砸成功开始；
动作被强制中断。
```

短暂改变移动方向、自动切换目标或者原目标死亡，不应重置连段段位。

## 2.3 主动技能

大锤只保留两个主动技能：

```text
旋风
裂地重砸
```

现有五次有效命中积累一次震势的规则先保留。

两个主动技能继续共享同一份震势资源，释放其中任意一个后消耗一次震势。

## 2.4 旋风无敌

旋风从动作正式开始到动作结束，全程免疫敌方造成的：

```text
近战伤害；
远程投射物伤害；
怪物接触伤害；
敌方技能伤害；
对应的受击表现和受击音效。
```

地图环境、主动退出战场、开发者伤害等非敌方攻击来源默认不受本次无敌影响。

## 2.5 手机开箱验收

目标设备上打开宝箱时：

```text
不能出现肉眼可见停顿；
不能在开箱帧创建 Mesh、Material、Node 或 GPU Buffer；
掉落释放帧只允许进行一次渲染刷新；
只能上传新出现或发生变化的掉落槽位；
不能因为掉落物移动而每帧调用 onGeometryChanged；
```

# 三、第一部分：把上挑改成自动第三段连击

## 3.1 不要复用震势命中计数

当前 `hitCountValue` 同时负责主动技能震势进度。

不要用它判断自动上挑，否则主动技能资源和普通连段会互相污染。

在 `BattlefieldHammerActionState` 中增加独立字段：

```ts
private completedNormalSwingCount = 0;
```

取值只允许：

```text
0
1
2
```

其中 `2` 表示下一段应进入自动上挑。

## 3.2 普通攻击段位计数

当一段 `SwingLeft` 或 `SwingRight` 完成时：

```ts
this.completedNormalSwingCount++;
```

不要按命中怪物数量增加。

第三段自动上挑完成后：

```ts
this.completedNormalSwingCount = 0;
```

连段中断时同样归零。

## 3.3 修改动作转换

修改：

```text
assets/bundles/battlefield/equipment/combat/
battlefield-hammer-action-state.ts
```

当前普通横扫结束后直接调用 `beginQueuedSwing()`。

改为：

```ts
private beginQueuedAttack(previousWasLeft: boolean): void {
  const directionX = this.queuedDirectionX;
  const directionZ = this.queuedDirectionZ;
  this.clearQueuedSwing();

  if (this.completedNormalSwingCount >= 2) {
    this.beginAutomaticUppercut(directionX, directionZ);
    return;
  }

  this.beginAction(
    previousWasLeft
      ? WeaponAction.ChainPrepareRight
      : WeaponAction.ChainPrepareLeft,
    CHAIN_PREPARE_SECONDS,
    directionX,
    directionZ,
  );

  this.poseSideValue = previousWasLeft ? 1 : -1;
  this.alternateLeft = previousWasLeft;
  this.lockedHeading = Math.atan2(directionX, directionZ);
}
```

普通横扫完成逻辑调整为：

```ts
case WeaponAction.SwingLeft:
case WeaponAction.SwingRight:
  this.completedNormalSwingCount++;

  if (this.attackHeldValue && this.queuedSwing) {
    this.beginQueuedAttack(this.actionValue === WeaponAction.SwingLeft);
  } else {
    this.beginRecover(definition);
  }
  break;
```

## 3.4 自动上挑不得消耗震势

删除面向输入层的：

```ts
public requestUppercut(...)
```

改成状态机内部方法：

```ts
private beginAutomaticUppercut(
  directionX: number,
  directionZ: number,
): void {
  this.beginAction(
    WeaponAction.Uppercut,
    AUTOMATIC_UPPERCUT_DURATION,
    directionX,
    directionZ,
  );

  this.lockedHeading = Math.atan2(directionX, directionZ);
  this.poseSideValue = 0;
}
```

这里不得调用：

```ts
consumeMomentum()
```

## 3.5 上挑结束后允许继续连段

当前上挑完成后直接回到 Idle。

修改为：

```ts
case WeaponAction.Uppercut:
  this.completedNormalSwingCount = 0;

  if (this.attackHeldValue && this.queuedSwing) {
    this.beginAction(
      WeaponAction.ChainPrepareLeft,
      CHAIN_PREPARE_SECONDS,
      this.queuedDirectionX,
      this.queuedDirectionZ,
    );
    this.clearQueuedSwing();
  } else {
    this.beginRecover(definition);
  }
  break;
```

同时扩展 `canBufferNextSwing`：

```ts
public get canBufferNextSwing(): boolean {
  if (this.queuedSwing) {
    return false;
  }

  if (this.actionValue === WeaponAction.SwingLeft
    || this.actionValue === WeaponAction.SwingRight) {
    return this.duration - this.elapsed <= SWING_BUFFER_SECONDS
      || this.hitStopRemaining > 0;
  }

  if (this.actionValue === WeaponAction.Uppercut) {
    return this.duration - this.elapsed <= UPPERCUT_BUFFER_SECONDS;
  }

  return false;
}
```

# 四、第二部分：让自动上挑锤飞一片怪物

## 4.1 不再使用单条锤头胶囊作为唯一判定

当前上挑只在冲击时间查询锤头连续扫掠路径。

这会让命中范围偏窄。

自动上挑应使用人物前方的群体扇区查询：

```ts
query.originX = owner.positionX;
query.originZ = owner.positionZ;
query.directionX = actionState.directionX;
query.directionZ = actionState.directionZ;
query.reach = definition.reach
  * SLEDGEHAMMER_PROGRESSION.uppercutReachScale;
query.arcRadians = SLEDGEHAMMER_PROGRESSION.uppercutArcRadians;
```

推荐第一版参数：

```ts
uppercutReachScale: 1.08,
uppercutArcRadians: Math.PI * 0.72,
```

约为 130° 的群体上挑扇区。

使用：

```ts
monsters.collectMeleeHits(query, meleeHits)
```

将扇区内所有合法怪物全部写入上挑命中事件。

不要只选择锚点目标。

## 4.2 避免重复命中

一次自动上挑中的每只怪物只能结算一次。

继续使用：

```ts
attackSequenceId
acceptHitSequence(...)
```

不得因为锤头视觉扫掠和扇区辅助查询同时命中而结算两次。

建议自动上挑只使用扇区权威命中；锤头轨迹仅用于视觉调试。

# 五、第三部分：把垂直腾空改成斜向飞行

## 5.1 当前问题

现有效果把平面击退和垂直腾空拆成两个独立效果：

```text
平面击退很快衰减；
Y 轴腾空持续更久；
```

结果看起来接近原地垂直起飞。

应新增真正的三维方向腾空效果。

## 5.2 新增效果契约

修改：

```text
assets/core/contracts/monster-effects.ts
```

新增：

```ts
export interface DirectionalLaunchEffect {
  readonly directionX: number;
  readonly directionZ: number;

  /** 水平初速度。 */
  readonly horizontalSpeed: number;

  /** 垂直初速度。 */
  readonly verticalSpeed: number;

  readonly horizontalDrag: number;
  readonly gravityScale: number;
  readonly resistanceScale: number;
}
```

在 `BattlefieldHammerCombatTarget` 中增加：

```ts
applyDirectionalLaunch(
  populationId: number,
  entityId: number,
  effect: Readonly<DirectionalLaunchEffect>,
): boolean;
```

上挑不再分别调用普通 `applyKnockback` 和 `applyVerticalLaunch`。

## 5.3 Effect SoA 状态

在 `BattlefieldMonsterEffectGroupState` 中增加：

```ts
airborneVelocityX: Float32Array;
airborneVelocityZ: Float32Array;
airborneHorizontalDrag: Float32Array;
```

方向上挑时写入：

```ts
state.airborneVelocityX[id] =
  effect.directionX
  * effect.horizontalSpeed
  * resistance;

state.airborneVelocityZ[id] =
  effect.directionZ
  * effect.horizontalSpeed
  * resistance;

state.verticalVelocity[id] =
  effect.verticalSpeed
  * resistance;
```

怪物腾空期间每帧推进：

```ts
crowd.x[id] += airborneVelocityX[id]
  * deltaTime
  * inverseScale;

crowd.y[id] -= airborneVelocityZ[id]
  * deltaTime
  * inverseScale;

const damping = Math.exp(
  -airborneHorizontalDrag[id] * deltaTime,
);

airborneVelocityX[id] *= damping;
airborneVelocityZ[id] *= damping;
```

落地时清空三轴速度。

## 5.4 每只怪物的飞行方向

每只怪物不能完全沿同一条直线飞，否则会叠在一起。

计算：

```ts
const radialX = targetX - owner.positionX;
const radialZ = targetZ - owner.positionZ;
const radialLength = Math.hypot(radialX, radialZ);

const radialDirectionX = radialLength > EPSILON
  ? radialX / radialLength
  : actionState.directionX;

const radialDirectionZ = radialLength > EPSILON
  ? radialZ / radialLength
  : actionState.directionZ;
```

然后把攻击方向和怪物径向方向混合：

```ts
const launchX =
  actionState.directionX * 0.65
  + radialDirectionX * 0.35;

const launchZ =
  actionState.directionZ * 0.65
  + radialDirectionZ * 0.35;
```

归一化后作为该怪物的实际受击方向。

这样整片怪物会大体向锤击方向飞，同时形成自然扇形扩散。

## 5.5 推荐配置

在 `SLEDGEHAMMER_PROGRESSION` 中增加：

```ts
uppercutReachScale: 1.08,
uppercutArcRadians: Math.PI * 0.72,
uppercutLaunchHeight: 4.2,
uppercutHorizontalSpeed: 9.2,
uppercutHorizontalDrag: 1.15,
uppercutDamageScale: 1.2,
```

垂直速度继续通过目标高度计算：

```ts
calculateLaunchVelocity(
  gravity,
  uppercutLaunchHeight,
)
```

# 七、第五部分：两枚技能按钮圆弧平均分布

## 7.1 布局函数支持动态数量

将：

```ts
calculateBattlefieldRadialSkillLayout(
  centerX,
  centerY,
  orbitRadius,
)
```

改为：

```ts
calculateBattlefieldRadialSkillLayout(
  centerX: number,
  centerY: number,
  orbitRadius: number,
  skillCount: number,
): readonly Readonly<BattlefieldRadialSkillPosition>[]
```

## 7.2 使用圆弧分段中心

沿现有左侧到上侧的 90° 圆弧排列。

```ts
const ARC_START = Math.PI;
const ARC_LENGTH = Math.PI * 0.5;

for (let index = 0; index < skillCount; index++) {
  const amount = (index + 0.5) / skillCount;
  const angle = ARC_START - ARC_LENGTH * amount;

  positions[index] = Object.freeze({
    x: centerX + Math.cos(angle) * orbitRadius,
    y: centerY + Math.sin(angle) * orbitRadius,
  });
}
```

两枚技能得到：

```text
157.5°
112.5°
```

它们关于 135° 的左上对角线对称。

不要简单使用旧的 `position: 0` 和 `position: 1`，否则两枚按钮会挤在左侧和左上侧。

## 7.3 HUD 根据装备技能数量重新排版

```ts

```

`setLayout()` 只更新参数，然后调用：

```ts

```

`presentProfile()` 配置技能后也调用：

```ts
reflowActiveButtons()
```

按钮排列以 `profile.skills` 数组顺序为准，不再要求技能提供固定位置。

建议删除：

```ts

```

保留最多三枚按钮的池即可，未使用按钮保持隐藏。

# 九、第七部分：旋风重复命中累积击退速度

## 9.1 当前覆盖模式保留给普通攻击

新增：

```ts
export enum PlanarKnockbackCombineMode {
  Replace = 'replace',
  Accumulate = 'accumulate',
}
```

扩展 `PlanarKnockbackEffect`：

```ts
readonly combineMode: PlanarKnockbackCombineMode;
readonly maximumSpeed: number;
```

普通横扫、上挑之外的普通击退和重砸继续使用：

```ts
Replace
```

旋风使用：

```ts
Accumulate
```

## 9.2 计算当前实际速度

现有击退速度会随剩余时间线性衰减。

累积前先计算当前有效速度：

```ts
const remaining =
  state.knockbackRemaining[entityId] ?? 0;

const duration = Math.max(
  state.knockbackDuration[entityId] ?? remaining,
  EFFECT_EPSILON,
);

const currentSpeed =
  (state.knockbackSpeed[entityId] ?? 0)
  * remaining
  / duration;
```

## 9.3 进行速度向量叠加

```ts
const currentVelocityX =
  (state.knockbackDirectionX[entityId] ?? 0)
  * currentSpeed;

const currentVelocityZ =
  (state.knockbackDirectionZ[entityId] ?? 0)
  * currentSpeed;

const addedSpeed =
  effect.initialSpeed
  * resistance;

const nextVelocityX =
  currentVelocityX
  + effect.directionX * addedSpeed;

const nextVelocityZ =
  currentVelocityZ
  + effect.directionZ * addedSpeed;

const rawSpeed = Math.hypot(
  nextVelocityX,
  nextVelocityZ,
);

const nextSpeed = Math.min(
  rawSpeed,
  effect.maximumSpeed,
);
```

速度大于零时重新归一化方向。

每次成功累积后：

```ts
state.knockbackRemaining[id] = Math.max(
  remaining,
  effect.remainingSeconds,
);

state.knockbackDuration[id] =
  state.knockbackRemaining[id];
```

## 9.4 旋风参数

在 `SLEDGEHAMMER_PROGRESSION` 中增加：

```ts
spinKnockbackCombineMode:
  PlanarKnockbackCombineMode.Accumulate,

spinMaximumKnockbackSpeed: 28,
spinPulseKnockbackScale: 0.62,
spinFinalKnockbackScale: 1.28,
```

旋风脉冲重复命中同一目标时，目标速度必须逐次上升。

最终重击同样在现有速度上继续叠加，而不是覆盖。

## 9.5 方向变化

如果目标被旋风不同方向重复击中，使用速度向量相加后的新方向。

这会自然产生类似踢球的效果：

```text
同方向继续命中：越来越快；
侧向再次命中：轨迹发生偏转；
反方向命中：先减速，再反向；
```

不得只简单执行：

```ts
oldSpeed + newSpeed
```

同时继续使用旧方向。

## 10.2 同一帧只允许一次渲染刷新

当前 `spawnBurst()` 内部立即调用 `synchronizeRendering()`，随后同一帧 `DroppedEquipmentPopulation.update()` 又调用一次。

删除 `spawnBurst()` 内部的：

```ts
this.synchronizeRendering();
```

同时删除这些事务方法中的即时刷新：

```text
trySpawnPlayerDiscard
remove
removeOwned
```

改为只标记：

```ts
private renderingDirty = true;
```

在统一更新末尾刷新一次：

```ts
public update(deltaTime: number): void {
  for (...) {
    item.update(deltaTime);
  }

  if (this.renderingDirty || this.hasMovingItems) {
    this.flushRendering();
  }
}
```

宝箱更新顺序保持：

```text
宝箱释放掉落
→ 掉落物推进一次
→ 本帧统一刷新一次渲染
```

---

## 10.3 只上传脏槽位，不上传整个活动前缀

当前掉落渲染器即使只新增一件物品，也会上传从零到 `activeCount` 的全部顶点。

修改 `DroppedEquipmentRenderer.synchronize()`：

记录：

```ts
let firstDirtySlot = Number.POSITIVE_INFINITY;
let lastDirtySlot = -1;
```

每次 `writePose(index, item)` 时更新脏区间。

最后通过槽位顶点偏移计算：

```ts
const firstVertex =
  packedGeometry.vertexOffsets[firstDirtySlot];

const endVertex =
  packedGeometry.vertexOffsets[lastDirtySlot + 1];

batch.uploadVertexAttributeRange(
  MeshDirty.Position,
  firstVertex,
  endVertex - firstVertex,
);
```

`DroppedEquipmentAccentRenderer` 同样使用范围上传。

不得再使用：

```ts
uploadVertexAttributes(
  dirty,
  activeCount * verticesPerItem,
)
```

处理删除后末尾槽位回填时，脏区间必须同时覆盖：

```text
被回填槽位；
原末尾槽位。
```

---

## 10.4 停止每帧刷新动态包围盒

目前掉落物移动时会重新扫描全部活动物品、修改 Mesh bounds，并触发：

```ts
renderer.onGeometryChanged()
```

这在移动端可能产生明显 CPU 和渲染线程同步开销。

改为在加载阶段为掉落物批次创建保守固定包围盒。

包围盒范围应覆盖：

```text
活动 Chunk 窗口；
宝箱最大爆散距离；
掉落最大飞行高度；
玩家最大丢弃距离。
```

正常掉落飞行和落地过程中：

```text
不得调用 updateBounds；
不得调用 onGeometryChanged。
```

只有以下情况允许重算包围盒：

```text
活动 Chunk 窗口尺寸改变；
整个掉落人口重建；
场景重新加载。
```

项目当前只有两个掉落 Draw Call，使用稍大的保守包围盒比每帧刷新几何状态更合适。

---

## 10.5 真正预热第一次 GPU 绘制

当前预热只创建 Mesh、Material 和最大容量缓冲，但批次保持不可见。

移动端仍可能在第一件掉落物真正显示时编译 Shader/Pipeline State。

加载阶段增加一次真实绘制预热：

```text
写入一个临时掉落槽位；
把它放到地面下或相机外；
激活本体和信标的真实索引范围；
让引擎至少提交一个渲染帧；
下一帧清空活动索引并回收临时槽位。
```

预热必须覆盖：

```text
掉落物本体材质；
稀有度信标材质；
位置流更新；
颜色流更新；
实际索引拓扑。
```

如果 Cocos 当前版本提供官方 PSO/Shader 预编译接口，优先使用官方接口。

不得假设“创建了 Material”就等于已经完成 GPU Pipeline 预热。

---

## 10.6 开箱热路径不得创建引擎对象

在 `TreasureChestRuntime.open()` 和 `releaseLoot()` 中验证：

```text
没有 new Node；
没有 new Mesh；
没有 new MeshRenderer；
没有创建 Material；
没有创建 DynamicMeshBatch；
没有扩容 GPU Buffer；
```

当前单宝箱最大只掉落一件装备，因此普通 JS 小对象不是首要瓶颈。

优先修复：

```text
首次可见 Pipeline；
重复 GPU 上传；
整段前缀上传；
每帧 onGeometryChanged。
```

在这些问题解决后，再考虑把轨迹对象和运行时对象改成固定 SoA 池。

# 十二、性能验收标准

目标手机开启宝箱时：

```text
60 FPS 目标：
开箱造成的额外主线程耗时 p95 ≤ 2ms；
任何开箱帧总耗时不得超过 33.3ms。

30 FPS 目标：
不能因为开箱额外丢失完整一帧。
```

释放一件装备时：

```text
最多一次本体局部顶点上传；
最多一次信标局部顶点上传；
上传范围只覆盖一个新增槽位；
零次动态包围盒刷新；
零次引擎资源创建；
零次 GPU 缓冲扩容。
```

必须在至少一台 Android 中低端设备或等效降频环境中实际验证，不能只通过桌面单元测试判断卡顿已经解决。

# 十四、禁止实现

不得使用以下临时方案：

```text
只把上挑按钮隐藏，但仍保留可触发输入；
用命中怪物数量判断已经攻击了几下；
让第二段普通横扫直接垂直抬高所有怪物；
只增加 Y 速度而不增加水平飞行速度；
旋风期间只把承伤从45%改成很小的数；
每次旋风命中直接覆盖怪物旧击退速度；
两个技能继续占用旧位置0和1；
通过减少宝箱动画或取消掉落特效掩盖卡顿；
把掉落释放拆到 setTimeout 或不可控异步任务；
在每次开箱时重新创建渲染节点和材质。
```

最终体验应该是：

```text
玩家连续抡两锤清理怪群，
第三锤自然向上掀飞整片怪物；
怪物沿受击方向呈扇形飞散；
旋风期间玩家可以无伤冲进怪群，
同一目标被反复击中后越飞越快；
技能区只有两枚整齐对称的主动技能；
手机打开第一个和后续宝箱都不会出现停顿。
```
