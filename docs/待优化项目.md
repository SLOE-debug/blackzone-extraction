# 一、怪物停止移动，但仍从“虚空”攻击

## 核心判断

这不是怪物 AI 全部停止，而是：

> **怪物权威模拟仍在移动和攻击，但 Curve Crawler 的 GPU 可视姿态停止更新。**

你的现象与代码架构完全吻合：

```text
Simulation
  BattlefieldMonsterWorldSystem
    → monsters.simulate()
      → group.update()
        → population.simulate()
        → CombatSystem 产生攻击伤害

RenderPreparation
  BattlefieldMonsterRenderingWorldSystem
    → monsters.synchronizeRendering()
      → CurveCrawlerSharedRenderer.synchronize()
        → 打包 Pose Texture
        → Texture2D.uploadData()
```

怪物模拟阶段会持续更新目标、行为、移动，并聚合攻击伤害。 怪物显示则在另一个独立的 `RenderPreparation` 系统中更新。

所以会出现：

```text
逻辑位置：已经走到玩家身边
渲染位置：仍停留在之前的位置
攻击判定：使用逻辑位置
玩家看到：远处怪物不动，但自己受到伤害
```

这正是“虚空怪物攻击”。

---

## 最可疑的故障点：GPU Pose Texture 更新链

Curve Crawler 的世界位置没有直接写入 Mesh 顶点，而是每帧打包到一张 `RGBA32F` 浮点纹理。权威的 `transform.x/y` 会被写入姿态纹理。

最终上传入口只有：

```ts
this.texture.uploadData(this.buffer.data);
```

而每个怪物群自己的 `rendering.update()` 在共享 GPU 渲染模式下其实是空方法：

```ts
public update(): void {
  // 共享 GPU 渲染器在统一同步点读取 SoA 姿态参数。
}
```

也就是说，共享渲染器的统一同步一旦失效，没有第二条路径能更新怪物位置。

你切出页面再切回来后，显示会突然刷新一次，非常像以下情况之一：

1. Cocos/WebGL 恢复时重新绑定了 Pose Texture。
2. 材质描述符或纹理资源恢复后，当前完整姿态被重新提交。
3. GPU 纹理上传在运行一段时间后停止生效，但没有抛出 JS 异常。
4. 页面恢复触发了一次纹理或批次重新创建，随后连续上传又再次失效。

这是根据代码路径和症状做出的高置信度推断；要确定具体属于哪一种，需要加入上传版本号和真机日志。

---

## 为什么不是单纯的 AI 卡死

怪物攻击伤害由模拟系统产生，并在另一个世界系统里应用。`BattlefieldMonsterWorldSystem` 每帧调用 `monsters.simulate()` 并保存攻击伤害。

Curve Crawler 的战斗系统只有在怪物的逻辑位置进入攻击范围时，才会进入咬击并产生伤害。

因此，怪物还能持续命中玩家，说明至少以下内容仍在运行：

* 目标同步；
* 行为/战斗时间轴；
* 权威位置或攻击距离；
* 攻击伤害结算。

停下来的主要是画面。

---

## 另一个必须修的隐患：用浮点高度判断“是否可移动”

最新实现中，只要：

```ts
effects.rootElevation[index] > 0
```

怪物就会：

* 停止行为；

* `currentSpeed = 0`；

* 停止移动；

* 退出战斗。

这不是当前“虚空攻击”的主要解释，因为处于该状态的怪物理论上不会继续攻击，但它仍然可能制造另一类永久僵死：

* 腾空高度留下极小正数；
* Entity 槽位复用时 Effect 状态没有完全清理；
* `setEffectElevation()` 某帧失败；
* 浮点积分无法精确回到零。

当前 Effect 积分虽然会尝试把落地高度归零，但玩法状态仍不应该用浮点值表达。

应改成：

```ts
AirborneEffect {
  active: Uint8Array;
  elevation: Float32Array;
  verticalVelocity: Float32Array;
}
```

移动、行为、战斗读取 `active`，而不是读取 `elevation > 0`。

## P0 修复方案

### 1. 先加入三套版本号

```ts
simulationPoseRevision
packedPoseRevision
gpuPoseUploadRevision
```

每帧记录：

```text
实体 ID
权威 x/z
打包到纹理的 x/y
当前 visible
currentSpeed
engaged
attackTime
rootElevation
上传字节数
上传次数
```

共享渲染器已经暴露 `lastPoseUploadBytes` 和 `lastPoseUploadCalls`，可以直接接进性能面板。

最关键的断言：

```ts
if (
  authorityPositionChanged &&
  gpuPoseUploadRevision === previousGpuPoseUploadRevision
) {
  throw/report RenderAuthorityDesynchronization;
}
```

### 2. 增加显式的强制重同步

给 `CurveCrawlerSharedRenderer` 新增：

```ts
public forceResynchronize(): void {
  this.structureDirty = true;
  this.material.setPoseTexture(
    this.poseTexture.asset,
    this.entityCapacity,
  );
  this.uploadPoseTexture();
  this.batch?.uploadIndices(this.activeIndices.indexCount);
  this.batch?.setVisible(this.activeIndices.indexCount > 0);
}
```

并在以下事件触发：

```text
应用恢复前台
WebGL context restored
纹理 gfx 资源发生变化
连续 N 帧检测到模拟/显示版本不一致
```

当前场景的 `update()` 只会继续调用 `world.step()`，没有恢复前台后的 GPU 资源重同步协议。

### 3. 不再把 `Texture2D.uploadData()` 当成唯一可靠路径

中期应改为：

* 显式 gfx texture/buffer 更新；
* 双缓冲 Pose 数据；
* 或改成动态实例 Buffer；
* 只更新实际居民对应的行；
* 在资源失效时重新创建并重新绑定；
* 上传成功后再更新 `gpuPoseUploadRevision`。

至少不要“调用了 `uploadData` 就默认画面一定更新”。

### 4. 增加长期回归测试

必须有真机/浏览器运行测试：

```text
持续运行 5–10 分钟
怪物持续追踪移动玩家
怪物进出视锥
切换后台 5 秒、30 秒、2 分钟
恢复后继续运行
怪物腾空后槽位回收再复用
```

验收必须比较：

```text
权威位置 vs 打包位置
权威位置 vs 屏幕可视位置
攻击者逻辑位置 vs 当前显示位置
```

不能只断言“玩家受到了伤害”或者“模拟测试通过”。

# 二、右侧摇杆必须是三个独立按钮

你说得对，当前提交完全实现错了。

当前只有一个 `BattlefieldSkillButton`，并且：

* 短按触发 `Uppercut`；

* 长按触发 `Spin`；

* 两个技能被塞进同一个按钮。

HUD 也只创建了一个实例，并把它放在右摇杆右上方约 45° 的位置。

## 正确布局

以右摇杆中心为原点：

```text
                    [90° 上挑]
                         ●

              [45° 裂地重砸]
                    ●

      右摇杆中心 ○────────● [0° 旋风]
```

精确位置建议：

```ts
const orbitRadius = 118;
const diagonal = orbitRadius * Math.SQRT1_2;

button0.setPosition(
  joystickX + orbitRadius,
  joystickY,
);

button45.setPosition(
  joystickX + diagonal,
  joystickY + diagonal,
);

button90.setPosition(
  joystickX,
  joystickY + orbitRadius,
);
```

当前攻击摇杆的交互半径是 108，摇杆本体半径是 72，因此约 118 的按钮轨道可以贴着交互区外缘，又不会离摇杆太远。

## 三个按钮的技能映射

为了让按钮角度和技能动作方向一致：

* **0°：横扫旋风**
  旋转攻击、径向击退、开始瞬间锁朝向。

* **45°：裂地重砸**
  向前踏步并砸地，造成小范围震波、短暂减速或破甲。

* **90°：冲天上挑**
  前方窄扇形击飞，高度读取可升级变量。

三个都是独立按钮、独立 Node、独立 Touch ID，不使用长按识别，不共享点击区域。

## 输入结构

删除：

```ts
BattlefieldSkillButtonCommand.Uppercut
BattlefieldSkillButtonCommand.Spin
```

这种单值消费方式。

改成独立的一次性命令缓冲：

```ts
interface BattlefieldRadialSkillCommands {
  spinRequested: boolean;
  groundSlamRequested: boolean;
  uppercutRequested: boolean;
}
```

调用树：

```text
SkillButton0 TOUCH_END
SkillButton45 TOUCH_END
SkillButton90 TOUCH_END
  → BattlefieldRadialSkillButtons.consumeCommands()
  → BattlefieldWeaponInputWorldSystem
  → BattlefieldWeaponCommandBuffer
  → BattlefieldHammerActionState
```

技能是否共用“震势”是玩法资源设计问题，但 **UI 与输入绝对不能再通过短按/长按复用一个按钮**。

# 三、大锤挥动为什么像“绳子吊着旋转”

## 精确根因

代码设计上，大锤确实是挂在右手，而不是左手。武器根通过右手腕到右手掌的方向计算握点。

但现在的动画方式会让它视觉上像连在错误的手上。

### 问题 1：整把锤子只绕单一根节点旋转

当前动作只有一个 `actionRotation`：

```ts
Quat.multiply(composedRotation, rigRotation, actionRotation);
root.setRotation(finalRotation);
```

锤子的位置基本固定在手部根节点，挥动主要靠改变旋转。

横扫曲线甚至直接做：

```ts
yaw = -105 + 210 * smooth(t);
yaw =  105 - 210 * smooth(t);
```

旋转技能则是：

```ts
yaw = t * 1080;
```

这实际上就是：

> 把一根很长的锤子固定在一点上，然后疯狂转 Quaternion。

没有握点轨迹、手臂牵引、肩膀发力、锤头惯性或随动位移，所以自然像钟摆或绳子。

### 问题 2：左右挥动的角色手臂动作居然完全相同

这是最严重的错误。

角色姿态层把：

```ts
WindupLeft
WindupRight
```

都转换成同一个正数 `attackAmount`。

`SwingLeft` 和 `SwingRight` 也被转换成相同的数值。

因此：

```text
锤子：
  左挥时向一侧旋转
  右挥时向另一侧旋转

角色右臂：
  左挥和右挥走完全相同的动作
```

武器方向和手臂方向互相脱节，握持接触点看起来就会漂移。玩家视觉会把这种漂移理解成“锤子被某根线拴在身上”。

### 问题 3：人物与武器分别执行两套不一致的动画

人物右臂只使用一个通用的攻击强度，锤子则执行独立的巨大 yaw。当前单手重武器姿态虽然指定右臂参与、左臂不参与，但没有真正按照挥动方向求解右肩、肘部、手腕。

### 问题 4：命中发生在挥动刚开始时

当前从 Windup 切到 Swing 的那一帧，就立即发出 `swingImpact`。

也就是说：

```text
刚开始横扫
  → 已经伤害和击退怪物
  → 锤头视觉仍没有真正扫到目标
```

这进一步放大“挥动没有重量、锤子和伤害无关”的感觉。

### 问题 5：命中检测根本不读取锤头轨迹

现在的命中查询是：

```text
以玩家为圆心
按攻击方向查询扇形
在一个事件帧一次性结算
```

它不是：

```text
上一帧锤头位置
  → 当前帧锤头位置
  → Swept Capsule 连续扫掠
```

所以动画再怎么调整，伤害和锤头仍然可能对不上。

# 四、大锤动画必须重构为“握点约束 + 锤头轨迹”

## 正确层级

```text
Vanguard Right Hand
  → MainGripSocket
      → HammerGripPivot
          → HammerModel
```

锤子模型必须明确提供：

```ts
mainGripLocalPosition
hammerHeadLocalPosition
```

不能继续假设模型原点就刚好等于正确握点。

## 动作求解

每一帧先算两个世界点：

```text
GripPosition：右手 FK 输出
HeadPosition：当前动作曲线上的锤头位置
```

然后：

```text
handleDirection = normalize(HeadPosition - GripPosition)
hammerRotation = orientationFromHandleDirection(...)
hammerPosition = GripPosition - rotate(mainGripLocalPosition)
```

这样可以保证：

* 手始终握住锤柄；
* 锤头沿真实路径移动；
* 不会因为单纯旋转根节点而漂移；
* 左右挥动拥有真正镜像的动作。

## 横扫轨迹

左右分别使用独立曲线：

```text
Windup
  锤头收到角色右后方/左后方
  胸腔和肩部反向蓄力

Acceleration
  锤头沿椭圆弧加速
  右肘逐渐伸展
  胸腔跟随旋转

Impact
  锤头经过角色前方
  产生 Swept Capsule 命中

Follow-through
  锤头继续越过目标
  身体减速
  手腕回正
```

不要只给动作一个 `[0,1] attackAmount`。需要至少输出：

```ts
interface VanguardHammerPoseInput {
  action: WeaponAction;
  side: -1 | 1;
  phase: HammerActionPhase;
  progress: number;
}
```

`side` 必须一直传到胸腔、肩膀、肘部、手腕和锤头求解器。

## 时间建议

当前 0.18 秒蓄力、0.14 秒挥击过于轻快。

建议：

```text
蓄力        0.26–0.32s
加速/接触   0.18–0.22s
随挥        0.18–0.26s
恢复        0.10–0.16s
```

命中发生在加速/接触阶段的约 55%–65%，而不是进入 Swing 的第一帧。

## 连续碰撞

新增：

```ts
HammerHeadSweepState {
  previousX;
  previousY;
  previousZ;
  currentX;
  currentY;
  currentZ;
  radius;
}
```

命中调用树：

```text
HammerPoseSolver
  → 写入 previous/current hammer head

HammerMeleeSweepSystem
  → Swept Capsule Broadphase
  → 目标窄相位
  → attackSequenceId 去重
  → Damage
  → Knockback
```

视觉锤头和伤害锤头必须是同一份权威位置。

## 旋转攻击

旋转技能不能只是：

```ts
hammerYaw = progress * 1080;
```

正确方式是：

```text
锁定初始朝向
→ 角色胸腔、骨盆、右臂、握点和锤子整体旋转
→ 锤子只增加少量局部滞后
→ 玩家模型与锤子保持一个整体
```

否则永远像手腕上的螺旋桨。
